2.3 The PAY_n encoding is the crux of the whole project

The documented codes are −2 = no credit use, −1 = paid in full, 0 = revolving credit (paid the minimum), 1 = one month late, 2 = two months late, …, 8 = eight months late.

Read that again as a number line. It is an integer column, so any model will treat −2 < −1 < 0 < 1 < 2 as ordered and expect default risk to increase along it. But the observed default rate does not increase monotonically:

Interactive · the non-monotonicity

Observed default rate by PAY_0 code in the held-out sample, from results/exp11_shap.json. Hover a bar. Note the dip at code 0.

A client on revolving credit (0) is safer than one who paid in full (−1) in this sample. That is economically sensible — revolving borrowers are engaged, profitable, and screened; clients who clear the balance may be transactors with thin behavioural history — but it is not a monotone function of the code.

Three design consequences, all traceable to this one fact
  1. Prefer a non-linear learner. Logistic regression fits one coefficient per column, i.e. a monotone effect. It cannot represent a dip at 0. That is a structural limitation, not a tuning failure — and it is why the ladder's linear rung underperforms.
  2. Keep the native integers; don't one-hot. A tree makes axis-aligned splits, so a non-monotone response is recoverable by stacking splits (PAY_0 < 0.5, then PAY_0 < −1.5). That costs tree depth, not expressible functions. Verified empirically in §10.
  3. Expect SHAP to rediscover the dip. If the model has genuinely learned the shape, the attribution for code 0 should be the most negative of all codes. It is (§11) — which is convergent validation of the EDA from the model's internals.

The trend features: why the slope is one dot product

The six months are evenly spaced, so the OLS slope denominator is a constant and the whole regression collapses to a dot product. This is worth understanding because it is a nice example of exploiting structure instead of calling a library in a loop:

slope = Σᵢ (xᵢ − x̄)(yᵢ − ȳ) / Σᵢ (xᵢ − x̄)²

With x = [0,1,2,3,4,5], the denominator Σ(xᵢ − x̄)² is always 17.5. And because Σ(xᵢ − x̄) = 0, the ȳ term in the numerator cancels. So:

src/data.py_ols_slope()
_X_MONTH   = np.arange(6, dtype=float)
_X_CENTRED = _X_MONTH - _X_MONTH.mean()
_X_SS      = float((_X_CENTRED**2).sum())   # 17.5, a constant

def _ols_slope(values):
    """Least-squares slope of each row against the chronological month index."""
    v = np.asarray(values, dtype=float)
    return (v - v.mean(axis=1, keepdims=True)) @ _X_CENTRED / _X_SS

One vectorised matrix–vector product computes 29,944 regressions. Note it is fed PAY_CHRONO, not PAY_COLS — so a positive slope means deteriorating.

The NaN decision, and why it is a feature not a fudge

PAY_RATIO_n divides by the statement balance, which is zero or negative for 1,930 rows. The convention chosen is np.nan, not a sentinel fill:

safe_bills = np.where(bills > 0, bills, np.nan)   # NaN, not 0 and not -999
ratios = pays / safe_bills
Why NaN beats any fill value here

XGBoost handles missing values natively: at each split it learns a default direction for NaN rows by trying both and keeping whichever scores better (§3.6). So NaN means "the model decides what undefined means, per split, from the data." A fill value of 0 instead asserts "undefined behaves exactly like a client who paid nothing" — which is a claim about credit risk smuggled in as a preprocessing step. NaN carries strictly more information, and the fact that it works at all is a library capability worth describing in the Solution section.

Three assertions guard the output — the inf check matters because an unguarded division would produce infinities that silently poison the hist binning of §3.4:

assert len(added) == 17, f"Expected 17 engineered columns, got {len(added)}"
assert not np.isinf(out[added].to_numpy(dtype=float)).any(), "engineer() emitted inf"
Self-check: why not just one-hot encode PAY_0 to handle the non-monotonicity?

You could, and §10 measures it: one-hot reaches against native integers' — a difference far inside one fold-SD, so the two are indistinguishable. But one-hot costs you three things:

  • It inflates the feature count from 23 to , which dilutes colsample_bytree and slows every fit.
  • It destroys the ordinal information the tree could otherwise use — a split at PAY_0 < 2.5 captures "two or more months late" in one node; one-hot needs a separate dummy per code.
  • It fragments SHAP attribution across 10+ dummy columns, so the PAY_0 dependence plot — the single most valuable figure in the report — would no longer exist.

The deeper point: trees do not need the fix, because stacked axis-aligned splits already express non-monotone functions. One-hot solves a problem that linear models have.

Section 3How XGBoost actually works

This is the "investigation of the tool" half of the Solution section — half of 50 marks. The goal is not to recite that XGBoost is "an optimised gradient-boosting library" but to derive, from scratch, the formula it uses to choose a split, and then show where every hyperparameter you tuned appears in that formula.

3.1 Start with one decision tree

A decision tree partitions the feature space with axis-aligned cuts: each internal node tests one feature against one threshold (PAY_0 < 0.5), and each leaf holds a prediction. "Axis-aligned" matters — a tree cannot learn the diagonal boundary BILL_AMT1 > 2 × PAY_AMT1 in one cut; it must approximate it with a staircase.

Two properties of trees drive several decisions in this project:

Why trees need no feature scaling

A split asks only "is this value above or below a threshold?". Any strictly increasing transform of a feature — multiply by 1,000, take a log, standardise — produces the same ordering, so the same split is available and the same tree is learned. Trees are invariant to monotone feature transforms.

This is why Phase 1's recommendation to scale features applied to distance and gradient learners (k-NN, SVM, logistic regression) and not to this one. §10 proves it empirically: signed-log transforming every monetary column reproduces the baseline ROC-AUC to the digit ( vs ) — not approximately, identically, because the sorted order never changed.

The second property is the problem boosting exists to solve: a single tree deep enough to be accurate is deep enough to memorise noise. Constrain the depth and you underfit; release it and you overfit. Boosting escapes this by using many deliberately weak trees.

3.2 Boosting as additive training

An XGBoost model is a sum of K trees. For client i:

ŷᵢ = σ( Σk=1..K fk(xᵢ) )(1)
fk
the k-th tree; it outputs a real number (a leaf weight), not a class
Σ fk(xᵢ)
the margin, or raw score, in log-odds units
σ(z) = 1/(1+e−z)
the logistic function, mapping log-odds to a probability in (0,1)
Remember this: the trees live in log-odds space

The trees sum to a log-odds value; the sigmoid is applied once at the end. This single fact explains two later decisions: why SHAP explanations are computed in margin space (where they are exactly additive, §11.3), and why scale_pos_weight shifts probabilities without improving ranking (§8.4).

Trees are added one at a time, and earlier trees are never revisited. At round t the model is ŷ(t) = ŷ(t−1) + ft(x). So the only question each round is: given everything the model already predicts, what tree most reduces the loss?

That is why boosting is often described as gradient descent in function space. Ordinary gradient descent takes a step in parameter space; boosting takes a step by appending a function.

3.3 The objective: loss plus a complexity penalty

𝓛(t) = Σᵢ l( yᵢ , ŷᵢ(t−1) + ft(xᵢ) ) + Ω(ft)(2)

The first term is the training loss — for binary classification, log-loss. The second is where XGBoost departs from classical gradient boosting: an explicit penalty on the tree's own complexity, inside the objective that chooses the tree.

Ω(f) = γT + ½λ Σj wj² + α Σj |wj|(3)
T
number of leaves in the tree
wj
the output weight of leaf j
γ (gamma)
a flat toll charged per leaf — buys a split only if it pays for itself
λ (reg_lambda)
L2 shrinkage on leaf weights — pulls predictions toward zero
α (reg_alpha)
L1 shrinkage on leaf weights — can drive them to exactly zero
Say this in the report

Classical gradient boosting (Friedman, 2001) controls complexity externally — you cap the depth, or prune afterwards. XGBoost (Chen & Guestrin, 2016) puts Ω(f) inside the objective, so the split-selection criterion itself knows what a split costs. Regularisation stops being a post-hoc correction and becomes part of the learning rule. This is the single most important structural claim to make about the library.

3.4 The second-order trick

Equation (2) is awkward: ft sits inside the loss function, so you cannot solve for the best leaf weights directly. XGBoost's move is to replace the loss with its second-order Taylor expansion around the current prediction.

Recall the Taylor expansion of any smooth function: l(z + Δ) ≈ l(z) + l′(z)Δ + ½l″(z)Δ². Apply it with z = ŷᵢ(t−1) and Δ = ft(xᵢ):

𝓛(t) ≈ Σᵢ [ gᵢ ft(xᵢ) + ½ hᵢ ft(xᵢ)² ] + Ω(ft) + const(4)
gᵢ = ∂l/∂ŷ
the gradient — for log-loss, gᵢ = pᵢ − yᵢ, the signed error
hᵢ = ∂²l/∂ŷ²
the Hessian — for log-loss, hᵢ = pᵢ(1 − pᵢ)
What g and h mean, intuitively

gᵢ = pᵢ − yᵢ is how wrong the model currently is about client i, and in which direction. A confidently-correct client contributes ≈ 0.

hᵢ = pᵢ(1 − pᵢ) is maximal (0.25) at p = 0.5 and vanishes as p → 0 or 1. So h is a measure of how uncertain the model is. It behaves as a per-client weight: clients the model is unsure about carry more influence over the next tree's shape. This is why boosting naturally focuses on hard cases — and it is the reason min_child_weight, which thresholds Σh, is a far subtler control than "minimum samples per leaf".

Equation (4) is now a quadratic in the leaf weights, and quadratics have closed-form minima. Define for leaf j the sums over the clients that land in it: Gj = Σ gᵢ and Hj = Σ hᵢ. Ignoring α for clarity, the objective for that leaf is Gjw + ½(Hj + λ)w². Differentiate, set to zero:

w*j = − Gj / (Hj + λ) ⟹ best-case loss = − ½ · Gj² / (Hj + λ)(5)

Now λ's role is visible: it sits in the denominator of the leaf weight, shrinking every prediction toward zero, and the shrinkage bites hardest when Hj is small — i.e. in leaves supported by few or confidently-classified clients. Exactly where you want it.

3.5 The split-gain formula — the heart of the library

Substituting (5) into (4) for a candidate split of a node into left and right children gives the quantity XGBoost maximises:

Gain = ½ [ GL²/(HL+λ) + GR²/(HR+λ) − (GL+GR)²/(HL+HR+λ) ] − γ(6)

Read it as three terms: quality of the left child plus quality of the right child minus quality of the parent, then minus the per-leaf toll.

The decision rule

If Gain ≤ 0, don't split. γ therefore acts as a minimum improvement threshold: a split must earn more than γ to exist. This is pre-pruning built into the criterion — not a separate pruning pass.

Because hᵢ = pᵢ(1−pᵢ), a leaf containing 50 clients the model already classifies confidently (p ≈ 0.02) has ΣH ≈ 50 × 0.0196 ≈ 0.98, while a leaf with 20 genuinely ambiguous clients (p ≈ 0.5) has ΣH ≈ 20 × 0.25 = 5.0. The second leaf is smaller in rows but carries five times the Hessian mass.

min_child_weight therefore means "don't build a leaf unless there is enough uncertainty in it to justify the estimate" — which is a much better-targeted control on a 22%-positive problem than a row count. The plan predicted it would dominate the tuning importances on this argument. It placed third (§11.6) — a documented wrong prediction, which is good Summary material.

3.6 Four engineering features that make it fast and robust

(a) hist: approximate split finding

Exact split finding sorts every feature at every node — O(n log n) per feature per node. tree_method="hist" instead buckets each feature into at most 256 bins once, then scans bins: O(n) per node, with the gradient and Hessian sums accumulated per bin.

On this dataset the approximation is free — and that is a real argument

PAY_n takes 11 distinct values; EDUCATION 4; MARRIAGE 3; SEX 2. All are far below 256, so every distinct value gets its own bin and no information is lost at all for the features that carry most of the signal (§10 shows repayment status alone reaches ). Binning only approximates the continuous monetary columns, where the exact cut-point between two near-identical balances is not meaningful anyway.

This is what made the 150-trial search affordable at ~2.3 s per trial.

(b) Sparsity-aware default directions

At each split, rows with NaN in the split feature are sent to a learned default direction: XGBoost tries sending them all left, then all right, and keeps whichever yields higher gain. Missingness is handled per split, learned from data, at no preprocessing cost. This is the library capability that justifies the PAY_RATIO_n → NaN decision in §2.

(c) Shrinkage (eta) and column subsampling

Each new tree's leaf weights are multiplied by η before being added. Small η means each tree corrects only a fraction of the residual, so many trees are needed but none dominates — the boosting analogue of a small learning rate. Your tuner chose η = , near the bottom of its range, and compensated with trees.

(d) Early stopping

Rather than guessing the tree count, you cap it at 2,000 and stop when a held-out metric fails to improve for 50 rounds. Where that held-out slice comes from is a leakage question, and §5 treats it as one.

API trap: XGBoost 2.0 moved these to the constructor

In XGBoost 1.x, early_stopping_rounds and eval_metric were arguments to .fit(). Since 2.0 they belong in the constructor. Older tutorials pass them to .fit(), where they are silently ignored — so the booster quietly optimises the default metric and never stops early. Nothing errors. You just get a worse model.

The second version trap — a real bug you hit and fixed

enable_categorical defaults to True in xgboost 3.4. And shap 0.52 reads that flag alone — not whether any column is actually of category dtype — to decide the model has categorical splits, then refuses interventional TreeSHAP with NotImplementedError: Categorical split is not yet supported.

Every numeric model therefore pins enable_categorical=False explicitly. Only the deliberate categorical arm of the encoding ablation sets it True, and that arm is not explained with interventional TreeSHAP. This is recorded in SETUP.md — a concrete, dated, version-specific interaction between two libraries is exactly the sort of detail that demonstrates real engagement with the tool.

Thread oversubscription

n_jobs=-1 lets XGBoost use every core. Optuna is therefore run with n_jobs=1 — a single process. Running both in parallel would spawn cores × cores threads fighting over the same CPUs, which is reliably slower than either alone.

Self-check: why is the second-order expansion worth the extra complexity over first-order?

Three reasons, in increasing importance:

  1. Closed-form leaf weights. A first-order approximation is linear in w, which has no finite minimum — you must pick a step size heuristically. The quadratic in (4) has the exact minimiser (5). No line search.
  2. A principled split criterion. Equation (6) falls out of (5) directly. Classical gradient boosting has to borrow a criterion (variance reduction, Gini) that is not derived from the loss being minimised.
  3. The Hessian is a useful curvature signal in its own right. Because h = p(1−p), it automatically weights clients by model uncertainty, and gives min_child_weight a meaning no row count can express.

Newton's method converges faster than gradient descent for the same reason — second-order information tells you how far to step, not just which way.

Self-check: what is the relationship between eta, n_estimators and overfitting?

They trade off almost exactly. Total model capacity is roughly η × K: halving η and doubling K gives a similar fit, but the small-η version is smoother, because no single tree can move the prediction far.

So you never tune K directly. You cap it high (2,000), tune η, and let early stopping discover K. Your tuner chose a low η = and early stopping settled on trees — the signature of a problem where signal is modest relative to noise, so slow and heavily-regularised beats fast and flexible.

This also explains the single largest finding in §7: library defaults use η = 0.3 and a fixed 100 rounds with no early stopping. Most of the measured tuning gain comes from fixing those two things, not from locating a precise optimum in eight dimensions.

Section 4Measuring honestly: what each metric can and cannot see

Every metric is a lossy summary. Pick the wrong one and a broken model looks excellent; pick one and report it alone and you will be unable to answer the obvious question in the viva. This section derives the four metrics the project reports — ROC-AUC, PR-AUC, Brier and ECE — from the confusion matrix, shows exactly what each is blind to, and demonstrates the blindness on your own numbers.

4.1 The accuracy trap, with the actual number

The dataset is defaulters. So a model that is a constant — predict "no default" for every single client, read no features at all — is right of the time.

Rung 0 exists to make this unarguable

The complexity ladder's first rung is DummyClassifier(strategy="most_frequent"). It scores accuracy and 0.0% recall: it catches zero defaulters. Its ROC-AUC is exactly 0.500, because a constant score cannot rank anybody above anybody else.

Compare the tuned model at the default threshold: accuracy. The tuned ensemble is four-tenths of a percentage point more accurate than a model that does nothing. If accuracy were the metric, the entire project would be worth 0.4 pp. It is the wrong metric — and the reason it is wrong is that it weights a missed default and a rejected good customer identically, which no lender does.

4.4 ROC-AUC from first principles

Sweep τ from 1 down to 0. At each value plot (FPR, recall). The curve traced out is the ROC curve; the area under it is ROC-AUC. Two facts make it the project's primary metric, and both are worth being able to derive on demand.

Fact 1 — AUC is a probability, via Mann–Whitney

Draw one defaulter and one non-defaulter uniformly at random. Then

ROC-AUC = P( score(defaulter) > score(non-defaulter) ) + ½·P( tie )(10)

Sketch. Order all n clients by score. A threshold placed between two adjacent clients corresponds to one point on the ROC curve, and stepping past a positive moves the curve up by 1/P while stepping past a negative moves it right by 1/N. The area accumulated by one rightward step is (number of positives already above) / P × 1/N. Summing over all negatives counts every (positive, negative) pair in which the positive outranks the negative, divided by P·N — which is exactly the pair probability above. The AUC is the normalised Mann–Whitney U statistic.

Three consequences you should be able to state. (i) 0.5 is chance, because a random ranking wins half the pairs — which is why rung 0 scores exactly 0.500. (ii) AUC depends only on the order of the scores, so any strictly increasing transform of the scores leaves it unchanged. (iii) It is computed within classes, so it does not move when prevalence does.

Consequence (ii) is not a curiosity — it is the load-bearing argument for two separate design decisions in this project, and both appear in the report's Solution section.

The invariance does real work twice
  1. It is why scale_pos_weight is excluded from the tuning search space (§7). Reweighting the positive class rescales the logits roughly monotonically, so it barely moves the order — and therefore barely moves ROC-AUC. A tuner optimising ROC-AUC is nearly blind to the parameter and would pick a value arbitrarily, which turns the imbalance study into a confound. Fixing it per arm and tuning each arm separately makes it a controlled comparison instead.
  2. It is why ROC-AUC alone is insufficient and Brier is mandatory (§9). Calibration is a monotone-transform property, so ROC-AUC cannot see it at all. §4.6 shows this on your own two arms.
Fact 2 — why ROC-AUC and not PR-AUC as the tuning objective

Three reasons, in the order they would be defended:

  • Comparability across the ladder. Prevalence-independence means rung 1 and rung 6 are measured on the same scale even though the folds differ slightly in composition.
  • Lower fold-to-fold variance. PR-AUC's precision term has the small positive count in its denominator, so it is noisier. Across your 25 repeated-CV fits the tuned model's ROC-AUC SD is ; optimising a noisier objective means the tuner spends trials chasing fold noise.
  • Precedent. Lessmann et al. (2015) benchmark credit-scoring classifiers on ROC-AUC, so reporting it keeps the result comparable to published work.

PR-AUC is still logged every trial and reported in every table — it is simply not the thing being maximised. "Log it, report it, do not optimise it" is the defensible position; reporting only the metric you optimised is not.

4.6 Brier score: the metric that sees what ROC-AUC cannot

The Brier score is the mean squared error of the probabilities themselves:

Brier = (1/n) Σᵢ (p̂ᵢ − yᵢ)²(11)

Lower is better. It is a strictly proper scoring rule: it is uniquely minimised by reporting your true believed probability, so you cannot improve it by shading your forecasts. And unlike ROC-AUC it is not invariant to monotone transforms — squash every probability toward 0.5 and the ranking is untouched while the Brier score degrades. That is exactly the sensitivity the project needs.

The decomposition that explains why

Murphy's decomposition splits the Brier score into three terms:

Brier = reliability − resolution + uncertainty(12)
reliability
(lower better) within each probability bin, the squared gap between the mean prediction and the observed rate — this is calibration error
resolution
(higher better) how far bin-wise observed rates spread away from the base rate — this is discrimination, the thing ROC-AUC measures
uncertainty
π(1 − π) at prevalence π; a property of the dataset, identical for every model, here

So Brier = discrimination and calibration in one number, which is both its strength and the reason the project also reports ECE: a single scalar cannot tell you which term moved.

4.7 Expected Calibration Error

Bin the predictions into B equal-width bins, and average the gap between predicted and observed within each, weighted by bin population:

ECE = Σb=1..B (nb/n) · | mean(p̂)b − rate(y)b |(13)

ECE is the reliability term of equation (12) made legible: an L1 average of vertical distances from the diagonal on a reliability diagram. The project uses B = 10.

Three honest caveats about ECE
  • It is bin-count-dependent. More bins means fewer clients per bin, noisier rates, usually a larger ECE. A quoted ECE is meaningless without its B.
  • It is not a proper scoring rule. A constant predictor that always outputs the base rate is perfectly calibrated and achieves ECE ≈ 0 while having zero discrimination. ECE must therefore always be read next to a discrimination metric — which is why the tables carry ROC-AUC, Brier and ECE together and never ECE alone.
  • Equal-width binning puts most clients in the first two bins at this prevalence, so the high-probability bins are sparse and their contribution is noisy. The reliability curves in §9 are plotted with their bin counts for exactly this reason.

The one-SD rule

Any gap smaller than roughly one fold-SD is reported as not distinguishable — stated in words, never bolded, never described as an improvement. The tuned model's SD is , so differences below about 0.007 ROC-AUC are noise. This rule is what makes the §8 imbalance result reportable as a mechanistic finding instead of a fabricated win.

Two further statistical points the project is careful about: (a) repeated-CV folds overlap, so a paired t-test across them is anti-conservative (Nadeau & Bengio, 2003) — the project notes this and leans on SD comparison instead; (b) DeLong's test is applied to exactly one comparison, tuned XGBoost against the PAY_0 baseline on the single held-out test set, because that is its actual use case: two correlated ROC curves on the same sample. Running it across CV folds would violate the independence its variance estimate assumes.

Self-check: someone reports "94% accuracy, up from 78%" — what do you ask?

What the recall is, and at what threshold. On this dataset 78% is the do-nothing constant, so the claim is that 16 pp of accuracy was gained — but accuracy can also be bought by making a model more conservative, which reduces recall. Then: what the cost assumption is, since accuracy weights a missed default and a rejected good customer identically. Finally: was the threshold 0.5, and was it chosen on the test set?

Self-check: two models have identical ROC-AUC to four decimals — can they behave differently?

Yes, in two distinct ways.

Calibration. ROC-AUC is invariant to monotone transforms, so one model's probabilities can be systematically inflated while its ranking is untouched. That is literally arms A and C in §4.6: indistinguishable ROC-AUC, Brier differing by .

Local ordering. Equal total area does not mean the same curve. One model can dominate at low FPR — where a lender actually operates — while the other catches up at high FPR and ends level. This is why PR-AUC and the operating-point confusion matrix are both reported rather than ROC-AUC alone.

Self-check: why is rung 0's PR-AUC equal to the prevalence while its ROC-AUC is exactly 0.5?

A constant score ranks nobody above anybody, so every randomly drawn (positive, negative) pair is a tie; by equation (10), AUC = ½ · P(tie) = ½ · 1 = 0.5.

For precision–recall, every threshold either flags everyone or nobody. When everyone is flagged, recall = 1 and precision = TP/(TP+FP) = prevalence. The curve is the horizontal line at precision = prevalence, so its area is the prevalence: = in the ladder JSON.

Section 5The evaluation protocol, and the five ways it could have leaked

A leaked number is not a slightly optimistic number — it is a number with no meaning, because it answers a question nobody asked ("how well does the model do on data it has already seen?"). This section builds the splitting architecture from the ground up, identifies every point at which information could flow backwards from the test set, and shows the specific line of code that blocks each one.

The invariant the whole architecture exists to protect

Every quantity used to make a choice — a hyperparameter, a feature set, a threshold, a calibration map, a stopping iteration — must be computed from data the final evaluation never sees. There are no exceptions and no "it only looked at it a little". A choice informed by the test set converts the test set into training data, silently and irreversibly.

5.1 Step zero: de-duplication happens before splitting

The Phase 1 cleaning pass removed duplicate feature-rows, taking 30,000 rows to . The ordering matters more than the count.

If two clients have byte-identical features and you split afterwards, one copy can land in train and the other in test. The model then "predicts" a row it has memorised, at zero generalisation. The inflation is not hypothetical: duplicates are not uniformly distributed — they concentrate among dormant accounts with all-zero bills, which are also the easiest rows to classify. Splitting after de-duplication makes train/test membership independent of the duplication structure.

Say this explicitly in the report. Markers look for it, and it is one sentence.

Why 20% is enough — the resolution calculation

The choice of test size is a bias–variance trade in disguise: more test data means a tighter estimate but a smaller training set. The right question is what difference do I need to be able to see? Hanley & McNeil (1982) give the standard error of an AUC estimate as

SE(A) = √[ ( A(1−A) + (P−1)(Q₁ − A²) + (N−1)(Q₂ − A²) ) / (P·N) ](14)
with  Q₁ = A/(2 − A),   Q₂ = 2A²/(1 + A)

Substituting A ≈ 0.78, P = positives and N = negatives gives SE ≈ 0.008. The differences the project needs to resolve on the test set are the ladder gaps — rung 1 to rung 6 is 0.140 AUC, roughly seventeen standard errors. Comfortably resolvable.

For the comparisons that matter, DeLong's paired estimator does better still, because the two ROC curves are computed on the same clients and their errors are positively correlated — the shared noise cancels. The reported paired SEs are 0.0040–0.0067, tighter than the 0.008 unpaired figure. That correlation is precisely why a paired test is the correct instrument here.

5.4 The nested problem: early stopping needs a validation set it must not have

src/runner.py — fit_one(), where the slice is carved
def fit_one(est, X_tr, y_tr, seed=SEED):
    """Fit a single estimator, carving the early-stopping slice out of the
    training data. The eval_set comes from an inner slice of this fold's *training*
    rows, so the outer validation fold is never seen by early stopping and the
    test set never at all."""
    if _uses_early_stopping(est):
        i_fit, i_es = train_test_split(
            np.arange(len(y_tr)), test_size=ES_SLICE,   # 0.15
            stratify=y_tr, random_state=seed,
        )
        est.fit(X_tr.iloc[i_fit], y_tr[i_fit],
                eval_set=[(X_tr.iloc[i_es], y_tr[i_es])], verbose=False)
    else:
        est.fit(X_tr, y_tr)
    return est
What this costs, and why it is worth it

Each fold now fits on 0.8 × 0.85 = 68% of the training data rather than 80%. Learning-curve evidence (§10) shows ROC-AUC has essentially plateaued by half the data, so the 12 pp sacrifice costs almost nothing measurable — while the alternative costs the validity of every number downstream.

Note also _uses_early_stopping(est): the branch is conditional. Logistic regression, the decision tree and the random forest have no eval_set concept, so they are fitted on the full fold. If the slice were carved unconditionally, the ladder's lower rungs would be handicapped by 15% of their data and the comparison that answers research question 1 would be unfair in XGBoost's favour.

5.5 Freezing the threshold — the leakage point that looks innocent

§4.3 established that the threshold is a separate decision. It is also a fitted decision, and therefore the most tempting place to leak, because the leak produces a beautiful number and no error message.

The fatal version, and why it is so seductive
# WRONG -- this is the single most common fatal flaw in this assignment
best = min(grid, key=lambda t: cost(y_test, p_test, t))
report(cost(y_test, p_test, best))

The threshold was chosen using the test labels, then scored against the same labels. You have reported the minimum of 51 draws rather than the value of a decision rule, so the figure is biased downward by construction and cannot be reproduced on new clients — the optimum will have moved. It looks innocent because no model was refitted; a single scalar was selected. One scalar is enough.

src/costs.py — pick_threshold_oof(), the correct version
def pick_threshold_oof(y_oof, proba_oof, r=R_HEADLINE, ead=None, grid=None):
    """Choose the cost-minimising threshold on out-of-fold TRAINING predictions.

    The returned scalar is frozen and applied unchanged to the test set."""
    grid  = threshold_grid() if grid is None else np.asarray(grid, dtype=float)
    costs = np.array([cost_at_threshold(y_oof, proba_oof, t, r=r, ead=ead)
                      for t in grid])
    tau   = float(grid[int(np.argmin(costs))])
    return tau, {"grid": grid.tolist(), "cost": costs.tolist(), "tau": tau}

Two details make this safe. proba_oof is assembled fold-by-fold inside cv_evaluate() — each client's probability comes from a model that never saw that client, so the sweep is genuinely out-of-sample within the training portion. And tau is returned as a Python float, which verify.py asserts is a scalar in (0, 1). A frozen scalar cannot accidentally be re-optimised later; an array could.

The threshold is then applied as an explicit comparison, never via .predict():

# .predict() silently uses 0.5 -- it would quietly discard the whole cost analysis

Leak. The tree count is a fitted parameter, and it was fitted on test labels. The model is now explicitly selected to stop at its best test performance. "Just" one integer is still a choice made from the test set.

SHAP values are computed on the test set after the model is finalised, and the resulting beeswarm appears in the report.

Fine. Nothing is selected — no refit, no re-threshold, no feature dropped on the basis of the plot. Leak — and the subtlest kind, because every individual evaluation was clean. Selecting the maximum of three test scores reports an order statistic, not an expectation: the winner's score includes whatever test-set noise favoured it. With SE ≈ 0.008 the expected optimism of a best-of-three is on the order of a standard error. Model selection belongs entirely in CV; the test set evaluates the already chosen configuration. This is why §5.6's third column is no in every row.

The cost-optimal threshold is chosen on out-of-fold predictions — but the out-of-fold predictions come from the tuned model, whose hyperparameters were selected on those same folds.

Leak, mild but real — and the project accepts it knowingly. The OOF probabilities are not fully out-of-sample with respect to hyperparameter selection, so the frozen τ is slightly optimistic. Removing it properly needs nested CV (tune inside each outer fold), which multiplies runtime by the fold count. The project's position: the bias is second-order because §7 shows the tuning surface is nearly flat (0.776–0.785 across 142 completed trials), τ is a one-dimensional choice on a 51-point grid rather than a nine-dimensional one, and §9 shows the chosen τ lands within 0.009 of Elkan's analytic optimum — a value that used no data at all. Naming a residual bias and bounding it is a stronger report than claiming none exists.

Section 6The complexity ladder: research question 1, quantified

Phase 1 asked whether the performance gain from ensembles justifies the loss of rule-based interpretability. Section 7Tuning: Bayesian search, and what it did not buy

Nine hyperparameters, an objective that takes two seconds to evaluate, and a budget. This section covers why Optuna's TPE rather than a grid, why ROC-AUC is the objective, why scale_pos_weight is deliberately absent from the search space, and the most important finding: the objective surface is almost flat, which is itself the evidence that the model is feature-limited rather than tuning-limited.

7.1 Why not grid search

The search space is eight-dimensional (nine with the tree count, which early stopping determines rather than the tuner). A grid with only four values per dimension is 4⁸ = 65,536 fits. At ~2.3 s per five-fold evaluation that is roughly 42 hours — for a grid so coarse it would probably miss the optimum anyway.

StrategyScalingProblem on this space
Grid searchexponential in dimensions infeasible past ~4 dimensions; spends equal effort on parameters that do not matter
Random searchlinear in budget works, and beats grid (Bergstra & Bengio, 2012) — but needs roughly 3× the trials for equal quality because it never learns from what it has already tried
TPE (Optuna)linear in budget, adaptive builds a density model of good vs bad regions and samples where improvement is likely; the chosen approach
How TPE actually works — enough to explain it in a viva

Tree-structured Parzen Estimator inverts the usual Bayesian-optimisation setup. Instead of modelling p(score | params) with a Gaussian process, it models the parameters given the score. After some startup trials it splits the history at a quantile y* (roughly the best 10%) and fits two kernel-density estimates:

ℓ(x) = p(x | score > y*)      g(x) = p(x | score ≤ y*)(15)

The next trial maximises the ratio ℓ(x)/g(x) — the region that is dense in good trials and sparse in bad ones. This is equivalent to maximising Expected Improvement, but it is cheap to sample from because one-dimensional KDEs can simply be drawn from and scored, with no matrix inversion. Hence "linear in budget" where a Gaussian process is cubic.

The project enables multivariate=True, which fits the densities jointly rather than per-parameter. That matters here because eta and the tree count genuinely interact, as do max_depth and min_child_weight — independent per-parameter densities cannot represent "low eta is good provided there are enough trees".

A log-uniform prior is correct when the parameter's effect is multiplicative — when 1 → 2 matters as much as 50 → 100. That is true of eta (halving the step size roughly doubles the trees needed), of reg_lambda and reg_alpha (regularisation strengths span four orders of magnitude and 0.01 vs 0.02 is a real difference while 99 vs 100 is not), and of min_child_weight.

It is wrong for subsample and colsample_bytree, which are fractions on a bounded interval where 0.6 → 0.7 and 0.9 → 1.0 are comparable moves; and meaningless for max_depth, which is a small integer. Searching λ uniformly on [0.01, 100] would put 99.99% of the prior mass above 0.01 × 10, so the tuner would essentially never try weak regularisation — and the chosen value () sits in a region a uniform prior would have found, which is a nice accident rather than a reason to have used one.

7.3 The objective, and the parameter deliberately left out

The objective is five-fold mean ROC-AUC on the selection folds, for the three reasons §4.4 derived. PR-AUC (aucpr) is logged every trial and reported in every table but never maximised.

The more interesting decision is an omission.

Why scale_pos_weight is not in the search space

This is the single best "justification of a design choice" in the Solution section, because it follows from a property of the metric rather than from a convention.

scale_pos_weight multiplies the gradient and Hessian contributions of positive rows. From equation (5), leaf weights are w* = −G/(H + λ), so weighting the positive class rescales the margins in a roughly monotone way. And by equation (10), ROC-AUC depends only on the order of the scores. A near-monotone rescaling barely changes the order, so ROC-AUC barely changes.

The consequence is not "it does not matter". The consequence is that the tuner cannot see it. Including a parameter the objective is blind to means the tuner picks a value essentially at random, and that arbitrary value then rides along into every downstream experiment — making every subsequent comparison a confound.

So it is fixed per arm and each arm is tuned separately: arm A at spw = 1, arm C at spw = (the neg/pos ratio), each with its own Optuna study and its own artifacts/best_params_*.json. That converts the imbalance question from a confound into the controlled comparison of §8. Then §9's Brier and ECE columns measure what ROC-AUC could not see — and they find a large effect, which is exactly why the parameter had to be handled outside the tuner rather than inside it.

Self-check: why is n_estimators not a tuned parameter?

Because early stopping determines it better than a search can. It is capped at 2,000 with early_stopping_rounds=50, and the actual tree count falls out of the fit — for the chosen configuration.

The reason this is strictly better: the optimal tree count is conditional on eta, since total capacity is roughly η × K. A tuner that searched both would waste most of its budget on (η, K) pairs that are jointly absurd — tiny η with few trees underfits badly, large η with many trees overfits — and the two parameters would have to be learned to be dependent. Letting early stopping resolve K for whatever η is proposed removes a dimension from the search and gives a better answer, because K is then chosen from data rather than from a grid.

The one thing this demands is care about which data: see §5.4. If the stopping set were the validation fold, K would be fitted on the fold it is scored against.

Section 8Class imbalance: the result that looks like nothing happened

The dataset is negatives per positive. Standard advice is to "fix the imbalance" with reweighting or oversampling. This section runs five arms, finds that reweighting changes ranking by less than a twentieth of one fold-SD, and argues that the right way to report this is as a mechanistic finding rather than a null one — because the same intervention wrecks calibration, which the cost analysis depends on.

8.1 What "imbalance" does and does not do to the model

Return to the gradient. For log-loss, gᵢ = pᵢ − yᵢ and hᵢ = pᵢ(1 − pᵢ). Nothing in the split-gain formula (6) references the class proportion; it references accumulated gradient and Hessian mass. So imbalance acts on the model through two indirect channels, and it is worth being precise about which:

the prior
the base margin starts at log(π/(1−π)), so the model begins by predicting roughly the base rate. Every subsequent tree learns deviations from it. This is a feature, not a problem — it is why the raw probabilities in §9 are nearly calibrated out of the box
leaf population
a pure-positive leaf is harder to form when positives are scarce, and min_child_weight is a Hessian floor that scarce positives struggle to clear. This is the real mechanism by which imbalance limits a boosted tree

What imbalance does not do is make the model "biased toward the majority class" in any sense a probability model can be biased. A model that outputs the correct conditional probability for every client is not biased; it simply outputs values below 0.5 for most of them. The problem people are usually describing is a thresholding problem, and §4.3 already separated that out.

3.5 : 1 is not a severe imbalance

Scale matters to the argument. Fraud detection runs at 1,000 : 1 and rare-disease screening at 10,000 : 1 — regimes where whole minority classes vanish from subsamples and specialised machinery is genuinely needed. At : 1 there are positives in the training portion. That is plenty. Framing prevalence as a pathology requiring intervention is the mistake this section is built to avoid.

8.4 The mechanism: two parameterisations of one decision

This is the explanation that turns three unremarkable rows into a result worth marks.

Why reweighting and threshold-moving are the same operation

Weighting positives by c multiplies their likelihood contribution, which is equivalent to fitting on a population where positives are c times more common. The fitted odds are therefore inflated by approximately c:

oddsweighted(x) ≈ c · oddstrue(x)(16)

Comparing the weighted probability against 0.5 means comparing weighted odds against 1, i.e. true odds against 1/c — which is exactly the test p ≥ 1/(1 + c) on the unweighted probabilities. Reweighting by c and thresholding at 0.5 implements the same decision rule as leaving the model alone and thresholding at 1/(1+c).

Check it against the data. With c = , the induced threshold is 1/(1 + 3.52) = 0.221. But the two routes are not equally good, and equation (16) says why: reweighting reaches the operating point by moving the probabilities, threshold-moving by moving the cut. Only one leaves a calibrated probability behind — and §9 consumes probabilities, not decisions. Hence the project's position: fit for probability, decide with a threshold.

How to say this in the report without claiming a null result

Weak version: "Reweighting did not improve performance." That reads as a failed experiment. Strong version: "Reweighting and threshold-moving are two parameterisations of the same decision shift — equation (16) shows scale_pos_weight = c with τ = 0.5 implements the same rule as τ = 1/(1+c) on unweighted probabilities, and arms B and C′ confirm it empirically by converging to within of each other on out-of-fold cost. Only threshold-moving preserves probability semantics (Brier vs ), and the cost-sensitive analysis consumes probabilities. Threshold-moving is therefore the strictly dominant choice, and the imbalance is handled at the decision layer rather than the fitting layer." Same numbers, and the second version demonstrates understanding of the mechanism.

8.5 Rejecting SMOTE — on this dataset's grounds, not generic ones

SMOTE (Chawla et al., 2002) creates synthetic positives by interpolating between a minority row and one of its minority neighbours: xnew = xi + λ(xnn − xi) with λ ~ U(0,1). Arm D scores , below the baseline — outside one fold-SD, so for once the difference is real and in the wrong direction.

The low score is not the argument, though. "It scored worse" is a weak rejection, because a different sampler or ratio might not have. The argument is semantic:

Interpolation produces repayment codes that do not exist

PAY_n is an ordinal status code, not a quantity: −2 = no usage, −1 = paid in full, 0 = revolving credit, 1…8 = months delinquent. Interpolating a client at PAY_0 = −1 with one at PAY_0 = 2 yields PAY_0 = 0.37.

There is no such repayment status. Worse, Phase 1 established that the default rate across these codes is non-monotonic — 12.8% at −1, 16.8% at 0, 34.0% at 1, 69.2% at 2. The midpoint between two codes is therefore not "between" them in risk either. The synthetic client is not a plausible-but-unobserved client; it is an impossible one, carrying a risk label interpolated along an axis that has no ordering in risk terms.

Six of the twenty-three features are PAY_n, and §10 shows they carry most of the signal. So SMOTE is corrupting precisely the columns that matter. That is a dataset-specific argument that survives the obvious follow-up question; "SMOTE overfits" does not.

And the generic argument, for completeness

Even setting semantics aside, SMOTE solves a problem this model does not have. Boosted trees already learn from gradient mass, and duplicating or interpolating minority rows multiplies that mass — which is what scale_pos_weight does directly, in one parameter, with no fabricated feature values. Arms C and D are attacking the same lever; one does it honestly. And arm D's Brier is — the worst of all five arms, because the model is now fitted to a resampled prevalence that does not match reality.

Section 9Calibration and cost: turning a score into a decision

A probability is a claim about the world: "18% of clients who look like this will default". That claim can be checked, and it must be, because the cost analysis multiplies it by a dollar figure. This section derives calibration, derives the cost matrix from credit-risk parameters rather than inventing it, derives Elkan's analytic threshold, and shows that the empirical and analytic optima agree — which is simultaneously a cost result and a calibration proof.

9.1 What calibration means, precisely

The definition

A model is calibrated if, for every value q, among all clients assigned probability q the observed default rate is q:

P( Y = 1 | p̂(X) = q ) = q   for all q(17)

Two things follow, and they are the reason both discrimination and calibration must be reported.

Calibration is not accuracy. A model that outputs the base rate for every single client is perfectly calibrated and completely useless — its ROC-AUC is 0.5. Calibration constrains the scale of the predictions; discrimination constrains their ordering. They are orthogonal, and a usable model needs both.

Discrimination is not calibration. §4.6 showed arms A and C with indistinguishable ROC-AUC and a 0.045 Brier gap. ROC-AUC literally cannot see the difference, because it is invariant to monotone transforms and miscalibration is a monotone transform.

9.3 Why the raw probabilities are already nearly calibrated

Arm A's raw ECE is and its mean prediction against a base rate of — out of the box, with no calibration step. That is not luck, and being able to explain why is worth more than the number.

Log-loss is a strictly proper scoring rule

XGBoost with objective="binary:logistic" minimises log-loss. A strictly proper scoring rule is uniquely minimised by reporting the true conditional probability — so a model trained to minimise it is trained toward calibration, not merely toward ranking. Add that the initial margin is log(π/(1−π)) (the base rate) and that a heavily regularised ensemble is reluctant to produce extreme values, and near-calibration is the expected outcome.

Contrast three models that are not calibrated by construction: an SVM (hinge loss optimises a margin, not a probability — hence Platt's original 1999 paper); a random forest (an average of votes, which compresses toward 0.5 and is over-confident at the extremes); and any model fitted with class weights, per equation (16). Arm C is the third case, and it demonstrates exactly the predicted failure.

9.5 The cost matrix, derived rather than invented

Picking "FN costs 5× FP" because it sounds plausible is the weakest possible move here: it is the one assumption the entire decision layer rests on, and an invented number makes every downstream figure arbitrary. So both costs come from standard credit-risk quantities.

Both sides of the matrix, from first principles

A false negative is a default the lender funded. The loss is the exposure at default multiplied by the fraction not recovered:

CFN = LGD × EAD,   LGD ≈ 0.70(18)

0.70 is the standard retail-unsecured loss-given-default: revolving credit-card debt is uncollateralised, so recovery is partial collection on a defaulted balance.

A false positive is a creditworthy client refused. Nothing is lost outright — the lender forgoes the margin it would have earned on that exposure:

CFP = NIM × EAD,   NIM ≈ 0.12(19)

0.12 is a representative net interest margin on revolving credit-card lending.

The ratio is what the threshold depends on, and the exposure term cancels out of it:

r = CFN/CFP = LGD/NIM = 0.70/0.12 = 5.83 → 6 : 1(20)
Why EAD cancelling is the important part

Equation (20) means the optimal threshold does not depend on how large the exposures are — only on the ratio of the two rates. That is why the headline analysis can use a flat per-error cost and still be defensible, and why the whole r sweep below is meaningful: r is a single interpretable dial encoding a lender's risk appetite, and a reader who disagrees with LGD = 0.70 can read their own row off the sweep rather than discarding the analysis.

The NT$1.17 bn figure is motivation, never a result

The proposal opened with a market-scale figure (9.8 M cardholders, NT$1.17 bn of defaulted balances). It belongs in the Introduction as motivation and nowhere else. Multiplying a cost saving measured on clients up to a national portfolio would require assuming this sample is representative of the whole market, that the model transfers across issuers, and that decisions scale linearly — none of which is established. The project reports cost on the actual evaluated clients, in error units and in LIMIT_BAL-weighted units, and stops there.

9.6 Elkan's analytic threshold

Derivation — four lines, and worth memorising

For a client with default probability p, compare the two expected costs:

E[cost | reject] = (1 − p) · CFP      E[cost | accept] = p · CFN

Rejecting is worth it when the second exceeds the first:

p · CFN > (1 − p) · CFP  ⟺  p · r > 1 − p  ⟺  p > 1/(1 + r)

So the optimal decision threshold is purely a function of the cost ratio (Elkan, 2001):

p* = 1/(1 + r)(21)

9.8 Instance-weighted costing

Flat costing assumes every client's exposure is identical, which is false: LIMIT_BAL spans NT$10,000 to NT$1,000,000. So the sweep is also run with per-client costs using LIMIT_BAL as an EAD proxy — total cost then sums over clients rather than being count × constant.

The effect is large and in a consistent direction. Under instance weighting the optimal threshold is at every cost ratio, because the objective is now dominated by a small number of high-limit clients and the ranking of whom to flag changes. Recall rises to .

Why both schemes are reported rather than just the better one

LIMIT_BAL is a proxy. The true exposure at default is the drawn balance at the moment of default, which is unobservable here — a client with a NT$500,000 limit carrying NT$3,000 of debt is not a NT$500,000 exposure. Using the credit limit systematically overstates exposure for low-utilisation clients, and §2 showed utilisation varies enormously.

So the flat scheme is the headline (defensible, no proxy assumption) and the instance scheme is reported alongside as a sensitivity. Reporting both, and naming the proxy's weakness, is stronger than picking whichever produces the more impressive saving — which would have been the instance scheme, and would have been the less defensible choice.

src/costs.py — the full decision layer in three functions
def cost_at_threshold(y, proba, tau, r=R_HEADLINE, ead=None):
    """Total cost of thresholding `proba` at `tau`. Flat unless `ead` is given."""
    pred = proba >= tau                       # never .predict()
    fn = (y == 1) & ~pred
    fp = (y == 0) & pred
    if ead is None:
        return float(r * fn.sum() + fp.sum())
    return float(r * ead[fn].sum() + ead[fp].sum())   # instance-weighted

def elkan_p_star(r=R_HEADLINE):
    """Elkan (2001) analytic optimum. No data, no model -- just the ratio."""
    return 1.0 / (1.0 + r)

Yes, and that is the whole point of costing the errors rather than counting them. At r = 6 one missed default costs as much as six unnecessary refusals, so trading one recovered default for up to six false positives is profitable. Low precision is not a defect here; it is the correct response to an asymmetric cost function. Self-check: why sweep r at all, instead of just reporting r = 6?

Three reasons, in increasing importance.

Robustness. LGD and NIM are estimates. A reader who believes LGD = 0.45 or NIM = 0.20 needs to know whether the conclusion survives, and the sweep answers that without re-running anything.

It is what makes the Elkan check possible. A single r gives one (τ, p*) pair, and one point proves nothing — any formula can match one point. Six ratios trace a curve, and the empirical optima tracking 1/(1+r) across the entire range is what turns coincidence into evidence. The mean absolute deviation of is a statement about the curve, not a point.

It separates the model from the policy. The sweep makes explicit that the model supplies a probability and the business supplies r. That is the correct division of responsibility, and it is exactly what a regulator reviewing an automated credit decision would want to see documented.

Self-check: if k = 3 months is within one SD of k = 6, why does the final model use all six?

Because "within one fold-SD" means not distinguishably worse, not better. The point estimate for k = 6 is still higher than k = 3 ( vs ), the data is already collected, and there is no cost to using it. Discarding available columns to chase parsimony the evidence does not demand would be the wrong move.

The recency finding is a statement about future data collection, not about this model: if a lender were specifying a new application-scoring pipeline, three months of statement history would capture nearly all the obtainable signal, and that is a real operational saving. That is why it lands in Summary — as a practical implication — rather than changing the final feature set.

Section 11SHAP: making an ensemble auditable

§6 established that the gain from boosting costs you direct readability. Research question 2 asks whether a post-hoc explanation can buy it back well enough for a regulator. That is a strong claim, so it needs a strong method — not a heuristic importance score, but an attribution with a uniqueness theorem behind it. This section builds SHAP from cooperative game theory, explains why it is computable on a tree ensemble at all, and then shows the model independently rediscovering a Phase 1 finding it was never told about.

11.1 The problem, stated precisely

The model outputs a number for one client. You want to split that number into 23 pieces, one per feature, such that the pieces sum to the output and each piece honestly represents that feature's contribution. Written down:

f(x) = φ0 + Σj=1..23 φj(24)
f(x)
the model's output for this one client
φ0
the base value — the output expected before seeing any feature
φj
the contribution of feature j, positive or negative

This is an additive feature attribution. The constraint that the pieces sum exactly to the output is what makes it auditable: nothing is unexplained, there is no residual "and then the model did something else".

Why the obvious approaches fail

"Drop the feature and see how much the prediction moves." This depends entirely on what you drop it with. If PAY_0 and PAY_2 both encode delinquency, dropping either one alone changes almost nothing (the other covers for it), so both look unimportant — yet dropping both is catastrophic. Marginal removal does not sum to the whole.

"Add the features one at a time and credit each with the jump." Better, but now the answer depends on the order you add them. Twenty-three features admit 23! orderings and they do not agree.

The resolution is the one Shapley found in 1953 for a different problem: average over all orderings. That removes the arbitrariness by construction rather than by convention.

11.2 The Shapley value, and why uniqueness matters

Cooperative game theory asks: n players cooperate to produce a payout; how should the payout be divided fairly? Map that onto the model: the players are the features, a coalition S is a subset of features, and the payout v(S) is the model's expected output when only the features in S are known. The Shapley value of player j is its average marginal contribution across every coalition it could join:

φj  =  ΣS ⊆ F \ {j}   [ |S|! · (|F| − |S| − 1)! / |F|! ]   ·   [ v(S ∪ {j}) − v(S) ](25)
F
the full feature set, |F| = 23
S
a coalition not containing j — the features already "revealed"
v(S ∪ {j}) − v(S)
j's marginal contribution when it joins coalition S
the bracketed weight
the fraction of the 23! orderings in which exactly the members of S precede j — this is what turns "it depends on the order" into a well-defined average

The reason to care is not that this formula is intuitive. It is that it is unique. Shapley proved it is the only attribution satisfying four properties simultaneously, and Lundberg & Lee (2017) imported that proof into machine learning:

The argument this licenses, in one sentence

"I used SHAP" is not an appeal to popularity. The claim available is: any attribution method satisfying those four properties is SHAP, so choosing a different method means giving one of them up — and you must then name which one. That is a much stronger position in a viva than "SHAP is the standard tool", and it is the kind of reasoning the Solution section rewards.

11.3 Why this is computable, and in which space

Equation (25) sums over all 2²³ ≈ 8.4 million coalitions, for every one of 2,000 clients. That is hopeless in general — exact Shapley values are NP-hard. TreeSHAP (Lundberg et al., 2020) exploits the structure of a tree to get the exact answer in polynomial time.

The structural insight

For a decision tree, v(S) has a closed form: push the client down the tree, and at any node that splits on a feature not in S, follow both children, weighting each by its training-data coverage. The expectation over unknown features becomes a weighted walk, not a Monte-Carlo integral.

TreeSHAP then pushes all coalitions down the tree simultaneously, carrying a bookkeeping structure that tracks, at each node, the weight each coalition size contributes. Cost drops from O(2M) to O(T · L · D²) — trees × leaves × depth². With trees at depth ≤ , that is seconds, not geological time. Exact, not sampled: this is why the additivity check below passes to machine precision rather than to a tolerance.

Explanations are computed in log-odds space

XGBoost's raw output is a margin: the sum of leaf weights across all trees, which is a log-odds value. The probability is obtained afterwards by the logistic link:

p = σ(m) = 1 / (1 + e−m)     m = Σt ft(x)(26)

The margin is a sum over trees, so additivity (24) holds exactly in margin space. σ is non-linear, so it does not commute with addition:

σ(φ0 + φ1 + φ2)  ≠  σ(φ0) + σ(φ1) + σ(φ2)(27)
The consequence, and the one exception made

Attributions in probability space are not additive, so a probability-space "explanation" of a sum is internally inconsistent — the pieces cannot be added up or compared across clients, because the same log-odds contribution maps to a different probability shift depending on where on the sigmoid the client sits. A client already at p = 0.85 and one at p = 0.03 experience the same +0.5 log-odds completely differently.

So exp11 computes and reports everything in log-odds (margin) space, verified: the maximum deviation of Σφ from the model margin across all explained rows is , which is floating-point noise. The single exception is the individual client waterfall in §11.8, where a probability is what a human actually wants to see — and there the non-additivity of the transform is stated on the figure rather than hidden.

SHAP is computed on stratified rows of the held-out test set, not on training data. §5.6's licensing table permits exactly this, and the permission is not a loophole — it is the point:

1

2

3

11.9 Two caveats that must travel with every SHAP claim

Caveat 1 — collinearity makes per-column BILL_AMT numbers unstable

BILL_AMT1 through BILL_AMT6 carry VIF 13.9–25.7 (Phase 1 Fig 2.14): consecutive monthly balances are nearly the same number. When several features carry near-identical information, a tree splits on whichever one happened to be available under colsample_bytree = , and TreeSHAP faithfully credits the column that was used. The split between members of the block is therefore partly arbitrary.

This is a statement about attribution, not about prediction. §10's ablations confirm the predictive consequence is nil — collinearity does not hurt a tree ensemble, which is why the columns are kept and why dropping them "because VIF is high" would have been the wrong move (§10.3).

The disciplined reading: BILL_AMT1 at rank 3 is not "the first bill matters and the others do not". It is "the balance block carries of the attribution and the model needs one representative of it". §12 quantifies the arbitrariness directly: across five reseeded refits the BILL_AMT columns show mean rank SD 1.73 against 1.16 for everything else. Predicted from the VIF, measured in the stability experiment.

Caveat 2 — SHAP attributes the model, not the world

SHAP answers "why did this model produce that output?". It does not answer "what would happen if we changed this feature?". The second is a causal question and needs an intervention, not an attribution.

LIMIT_BAL makes the distinction concrete. Its attribution is strongly negative for high limits. The causal reading — "raise this client's limit and they become less likely to default" — is almost certainly backwards: the bank granted a high limit because it had already judged the client low-risk, so the feature partly encodes a prior credit decision. SHAP cannot distinguish the two readings, and nothing in the SHAP machinery warns you.

Why this still satisfies research question 2. Q2 asks about decision auditability — can the institution explain, defensibly and reproducibly, why an applicant was declined? That is exactly the "why did this model decide that" question, and it is the one SHAP answers with a uniqueness theorem behind it. An adverse-action notice is a statement about the decision process, not a causal counterfactual. So the scope limitation is real and must be stated, but it does not undercut the claim being made. Overstating this is the most common way a good SHAP section loses marks.

Self-check: if SHAP is unique and provably fair, why does §12 bother testing its stability?

Because the uniqueness theorem is conditional on the model. SHAP gives the unique fair attribution for a given fitted model. It says nothing about whether a differently seeded fit of the same configuration on the same data produces similar attributions.

Those are different claims, and only the second one is what an audit trail requires. If re-running the pipeline with random_state=43 reordered the top ten features, then the explanation handed to a regulator would be an artefact of an arbitrary integer — provably fair with respect to a model that was itself arbitrary. That is why §12 exists, and why it is framed as testing whether the explanation is fit for audit rather than whether SHAP is correct.

Self-check: could you have used LIME instead, or permutation importance?

LIME fits a sparse linear surrogate in a neighbourhood of the client. It is model-agnostic, which is its appeal, but the explanation depends on a kernel width and a sampling distribution, both chosen by the analyst, and it satisfies local accuracy only approximately. Two analysts can produce two different LIME explanations of the same decision without either making an error. For a regulatory artefact that is a serious weakness, and for a tree ensemble it also gives up a large advantage: exactness is available here, so approximating is a pure loss.

Permutation importance is global only — it cannot explain an individual decision, which is the actual requirement. It is still computed in §12 as one of five importance measures, because it is held-out and prediction-based and therefore the natural partner to SHAP in the agreement analysis. But it cannot answer "why was this applicant declined", so it cannot stand in for SHAP here.

Self-check: the explained sample is 2,000 rows, not all 5,989. Does that weaken anything?

Not materially, and the reason is that every quantity reported from it is an average. The standard error of mean|SHAP| over 2,000 stratified rows is small relative to the gaps being discussed — PAY_0 at against LIMIT_BAL at is not a margin that 4,000 rows would overturn.

Where the sample size does bite is the sparse PAY_0 codes: 4, 5 and 8 hold 6, 1 and 1 rows respectively, and the full test set would roughly treble those counts while leaving them far too thin to be read as rates. That limitation is a property of the data — code 5 is rare in the population, not rare in the sample — so it is reported in §11.7 rather than fixed by explaining more rows. The interaction values in §12 are the part that is genuinely runtime-bound, and that is where the sampling decision actually pays for itself.

Section 12Is the explanation fit for audit?

§11 produced an explanation with a uniqueness theorem behind it. That theorem is conditional on the fitted model, which leaves the question an auditor actually cares about unanswered: would you get the same explanation if you re-ran the pipeline? And would you get the same answer if you had used a different importance measure? Two experiments, and the second one returns a result that should make anyone nervous about feature_importances_.

12.1 Stability under reseeding — the audit-trail test

Refit the final configuration with random_state ∈ {}, recompute SHAP for each fit, and compare the resulting global rankings. Nothing else changes: same data, same splits, same hyperparameters, same explainer configuration. Only the integer moves.

Why the seed moves anything at all

If boosting were deterministic the answer would be trivially "the same". It is not, because two tuned parameters inject randomness on every tree: subsample = draws a different row sample per tree, and colsample_bytree = draws a different column subset. So each seed explores a genuinely different sequence of trees, and when two features carry overlapping information the choice of which one a given tree splits on is decided partly by which was offered. The seed is not a formality here; it is the mechanism by which collinearity turns into attribution noise.

Two details that are easy to get wrong
  • booster.get_score() returns a dict keyed only by features that were actually split on. Converting it to an array with a plain list comprehension raises KeyError for any unused feature, and — worse — using dict.get(f) without a default silently yields None, which propagates into the Spearman computation as NaN and quietly poisons a whole row of the agreement matrix. The explicit 0.0 default is correct: never split on means zero importance, not missing importance.
  • permutation_importance is given X_val, not X_train. Permuting a column and measuring the training-score drop reports how much the model memorised through that column. That would convert the one unambiguously held-out built-in alternative into another in-sample measure and destroy the point of including it.

12.5 SHAP interaction values

Equation (24) attributes to single features. Shapley interaction values extend it to pairs, splitting each φj into a main effect plus pairwise terms, so that a feature's influence can be separated from its influence in combination with another:

f(x) = φ0 + Σj φjmain + Σj<k φjk(28)

The cost is a factor of M: the output is 23 × 23 per client rather than 23, and TreeSHAP's complexity gains a feature-count multiplier. exp12 therefore restricts interactions to the top five features — the plan listed this as runtime-permitting and it ran in overall.

The interaction that matters, and how to describe it carefully

The substantive pair is PAY_0 × PAY_2, which is exactly what §11.7's dependence plot is coloured by. The reading: a single month of delinquency is bad; a consecutive run is worse than the sum of its parts, because two months at code 2 is evidence of a persistent inability to pay rather than one missed cheque. An additive model cannot express that — it is precisely the non-additivity §6.5 measured as the gap between the logistic rung and the tree rung.

The caution: interaction values inherit every caveat of §11.9 and amplify the collinearity one, because pairs drawn from inside the BILL_AMT block are credit-splitting artefacts rather than findings. They are reported for the PAY_n block, where the columns are distinct ordinal codes with distinct meanings, and the monetary pairs are not interpreted individually. This is why the interaction result sits in the appendix with one sentence in the body rather than being promoted to a headline.

13.1 Why the Phase 1 baseline is what makes this interpretable

A fairness audit that reports "the model flags men more often than women" is uninformative on its own, because men in this dataset default more often than women. Without the baseline you cannot distinguish three completely different situations:

The model creates a disparity. Groups default at equal rates, the model treats them differently. Unambiguously a model defect.
B

C
The model amplifies a disparity. A real gap exists, and the model's decisions exaggerate it. This needs its own argument, because the amplification is the model's contribution and not the data's.

Why this is a strong result for the Summary

It is counter-intuitive, it is quantified, it is predicted by a paper the proposal already cited, and it only became measurable because §10.3's group ablation had already produced the no-demographics arm — the plan noted this was "one line of extra work" and it yielded the most interesting fairness finding in the project. It also reverses a plausible recommendation: the naive conclusion from the AUC cost would be "drop the demographics, they're free". The correct conclusion is to keep measuring them precisely because dropping them changes the decisions far less than it changes your ability to notice.

13.5 What this section does not claim

Scope, stated before someone else states it for you
  • No mitigation was applied. No reweighting, no per-group thresholds, no adversarial debiasing, no fairness-constrained objective. This is a measurement, which is what Phase 1 promised. Per-group thresholds would reduce the parity gap mechanically, but setting a different τ by sex is itself disparate treatment and is unlawful in most consumer-credit regimes — so it is not a neutral technical fix and would need a legal argument this project is not positioned to make.
  • "Amplifies" is not "causes". The disparity originates in the data. The amplification factor (× on SEX) is the model's contribution, and that is the number this project is answerable for.
  • The protected attributes are coarse. SEX is binary, EDUCATION is a four-level proxy for socioeconomic status, and the dataset is Taiwan 2005. Nothing here transfers to another population without re-measurement.
  • Intersectional gaps are not examined. Each attribute is analysed marginally. Subgroup sizes do not support a 2 × 4 × 3 × 4 cross-tabulation — the Wilson intervals would be wider than the effects — and claiming an intersectional result on a dozen clients per cell would be the kind of over-claiming §4.9 exists to prevent.

Sample size. The test set has rows, so EDUCATION level 3 and the MARRIAGE tail would be a few hundred clients each, with Wilson intervals wide enough to swamp every gap being discussed. 14.6 The ceiling: why ROC-AUC ≈ 0.78 and not 0.95

There are two explanations for a model that stops improving, and they imply opposite next steps. Model-limited means a better model or more data would help. Feature-limited means neither would. The distinction matters and can be settled with evidence already collected.

First, the irreducible-noise argument — and its honest size

The Bayes-floor check, reported as it came out

ComponentVersion

Recorded in the versions block of every results/*.json, per §3.2's schema. A number that cannot be tied to a library version is not reproducible, and xgboost in particular has changed defaults between major releases.

What re-running actually guarantees

  • Every number in the report is read back from results/ by src/report.py. Nothing is retyped, so a re-run that changed a number would change the report rather than silently disagree with it.
  • Total runtime across all fourteen experiments is on one laptop with tree_method="hist".
Self-check: the test AUC () is slightly below the CV mean (). Is that overfitting?

No — and the reasoning is worth having precise, because this is a question a marker is likely to ask. The gap is , which is well inside both the CV fold-SD () and the seed SD (). It is not a resolvable difference, and §4.9's rule forbids interpreting it as one.

Self-check: why is the isotonic-calibrated row's recall so much lower?

Because isotonic regression is a monotone re-mapping of the probabilities, so the same numerical τ sits at a different place in the score distribution. Its ROC-AUC is essentially unchanged ( against ) — as it must be, since ROC-AUC is invariant to monotone transforms (§4.4) — but at the frozen τ it flags far fewer clients, so recall drops and precision rises.

This is not a defect of isotonic calibration; it is the reminder that a threshold is only meaningful relative to the probability scale it was derived on. Pairing a τ frozen on raw probabilities with a recalibrated model is a mismatch, and the row is reported precisely to make that visible. A deployment choosing isotonic calibration would re-derive τ out-of-fold on the calibrated scores, and §9.7 shows that pairing actually tracks Elkan's analytic optimum more closely than the raw one does.

15.1 Why a package and not a notebook

Phase 1 was a notebook, and that was the right shape for it: 49 cells of exploration read top-to-bottom as an argument. Phase 2 is fourteen experiments totalling a couple of hours of compute, and a notebook is the wrong container for that for four independent reasons.

Problem with one notebookConsequenceWhat the package does instead

Rule 1 — there is exactly one evaluation path

Every experiment that reports a cross-validated number calls runner.cv_evaluate(). None implements its own loop. This is not a style preference. Divergent CV loops are the single largest source of numbers that cannot be reconciled later: one loop shuffles, another does not; one computes the mean of per-fold AUCs, another pools predictions and computes one AUC; one carves an early-stopping slice, another leaks the validation fold into it. All four produce plausible-looking ROC-AUCs that differ in the third decimal, and six weeks later nobody can say which table used which. One function means the comparison across all fourteen experiments is definitionally like-for-like.

Rule 2 — no number is ever retyped. Experiments write JSON; report.py and figures.py read it back. The report quotes results/manifest.csv. This very guide is built the same way — see §15.12. A number that appears in prose but not in a committed result file is, by construction, impossible.

Why CV_SEED = 7 rather than reusing 42

Why NaN and not a sentinel like -999 or 0

1,930 rows carry a negative BILL_AMT (Phase 1 §1.6) and many more carry exactly zero, so PAY_AMT / BILL_AMT is genuinely undefined for a substantial minority of clients — it is not a data error to be patched. Three options: fill with zero, fill with a sentinel, or emit NaN. Filling with zero lies: it asserts the client repaid nothing when in fact there was nothing to repay, and it places them next to genuine non-payers in the ordering. A sentinel like -999 is honest but forces the tree to spend a split separating the sentinel from the real values, and that split consumes depth. The NaN route is strictly better for this learner: XGBoost's sparsity-aware split finding (§3.6) learns a default direction for missing values at every node, at no cost in depth, choosing whichever side reduces loss more. So the undefined-ness is carried as information rather than destroyed. The isinf assertion then guarantees the guard actually worked — a division that slipped through as inf would propagate silently into the histogram builder.

The slope trick is a small thing worth noticing. Because the six months are evenly spaced, the denominator Σ(x−x̄)² is the constant 17.5 for every client, so the per-client OLS slope collapses to a single matrix–vector product rather than 29,944 calls to a regression routine. It is the difference between a few milliseconds and a few seconds, and more importantly it is one line that is obviously correct.

15.5 models.py — every estimator, constructed once

def xgb_classifier(params=None, spw=1.0, early_stopping=True,
                   enable_categorical=False, seed=SEED):
    """XGBoost with the project's fixed infrastructure settings.

    `early_stopping_rounds` and `eval_metric` go in the constructor, not `.fit()` --
    the XGBoost 2.x/3.x API moved them. `enable_categorical` is pinned False because
    xgboost 3.4 defaults it True and shap then refuses interventional TreeSHAP.
    """
    p = dict(XGB_FIXED)
    p["enable_categorical"] = enable_categorical
    p["random_state"] = seed
    p["scale_pos_weight"] = spw
    if early_stopping:
        p["n_estimators"] = N_ESTIMATORS_CAP
        p["early_stopping_rounds"] = ES_ROUNDS
    if params:
        p.update(params)
    return XGBClassifier(**p)
The API trap that silently does nothing

Almost every tutorial written before 2023 shows model.fit(X, y, early_stopping_rounds=50, eval_metric="auc"). In the XGBoost 2.x and 3.x scikit-learn API those two arguments moved to the constructor. Passing them to .fit() now raises a TypeError — which is the good outcome, because you find out immediately. The dangerous variant is omitting them entirely and assuming the n_estimators=2000 cap is being trimmed by early stopping when it is not: you then train two thousand trees on 24,000 rows, overfit substantially, and the only symptom is a mysteriously large train/CV gap. Note also what the early_stopping=True branch does — it sets n_estimators to the cap only when early stopping is active. Rung 5, the library-defaults rung, deliberately gets neither, because its entire purpose is to measure what you get with no tuning and no stopping at all.

The one custom estimator, and the one place it deliberately departs from the obvious design

src/models.pyexcerpt
class SmoteXGB(BaseEstimator, ClassifierMixin):
    """SMOTE + XGBoost, resampling strictly inside `fit`.

    Equivalent to an imblearn Pipeline for leakage purposes -- oversampling only ever
    sees the rows passed to `fit`, which cv_evaluate restricts to the fold's training
    half -- with one deliberate refinement: the early-stopping slice is carved off
    *before* resampling, so it retains the natural 22% prevalence. Validating against
    synthetically balanced data would make the stopping criterion measure the wrong
    distribution.
    """
    def fit(self, X, y):
        y = np.asarray(y).astype(int)
        i_fit, i_es = train_test_split(
            np.arange(len(y)), test_size=ES_SLICE, stratify=y, random_state=self.seed
        )
        X_res, y_res = SMOTE(random_state=self.seed).fit_resample(
            X.iloc[i_fit], y[i_fit]
        )
        self.model_ = xgb_classifier(self.params, spw=1.0, seed=self.seed)
        self.model_.fit(X_res, y_res,
                        eval_set=[(X.iloc[i_es], y[i_es])], verbose=False)
        self.classes_ = np.array([0, 1])
        return self
Why not simply imblearn.Pipeline([("smote", SMOTE()), ("xgb", ...)])

The pipeline is the standard answer and it is correct on the question everyone worries about: it resamples inside fit only, so synthetic minority rows never reach a validation fold, and the notorious failure of SMOTE-before-split is avoided. §8.5 explains why that failure is so severe — interpolating before splitting places synthetic points between a train row and a test row, and the model can then almost memorise the test set.

But the pipeline gets one secondary thing wrong here. XGBoost needs an early-stopping eval_set, and if that slice is taken from the pipeline's output it is 50/50 balanced synthetic data. Early stopping would then be minimising AUC against a distribution that does not exist, and would stop at the wrong tree count — not catastrophically, but wrongly, and in a way that would make arm D's comparison against A/B/C unfair. Carving i_es out first, at the natural prevalence, and resampling only i_fit, fixes it. This is the kind of detail that justifies writing twenty lines of custom estimator instead of using the one-liner: the one-liner is leakage-safe but distribution-wrong, and only one of those two is obvious.

15.6 runner.py — the single evaluation path

Rule 1 made concrete. Four functions matter.

fit_one — where the early-stopping slice is carved

src/runner.pyexcerpt
def fit_one(est, X_tr, y_tr, seed=SEED):
    """Fit a single estimator, carving the early-stopping slice out of the training data.

    The eval_set comes from an inner slice of this fold's *training* rows, so the outer
    validation fold is never seen by early stopping and the test set never at all.
    """
    if _uses_early_stopping(est):
        i_fit, i_es = train_test_split(
            np.arange(len(y_tr)), test_size=ES_SLICE, stratify=y_tr, random_state=seed
        )
        est.fit(X_tr.iloc[i_fit], y_tr[i_fit],
                eval_set=[(X_tr.iloc[i_es], y_tr[i_es])], verbose=False)
    else:
        est.fit(X_tr, y_tr)
    return est

Nine lines, and they are the implementation of §5.4. The arguments are already restricted to one fold's training half by the caller; fit_one splits that half again, 85/15, and uses the 15% purely to decide when to stop adding trees. Three distinct row sets are therefore in play per fold — fit rows, stopping rows, scoring rows — and each is used for exactly one purpose.

_uses_early_stopping is a two-line type check rather than a flag, which matters because the same function fits the dummy classifier, the logistic pipeline, the grid-searched tree, the random forest and the boosters. Non-XGBoost estimators take the else branch and get all the training rows, which is correct: handing a random forest an 85% subsample to match XGBoost would handicap it for no reason and corrupt the ladder comparison.

factory is a callable, not an estimator Calling factory() inside the loop builds a fresh estimator per fold. Passing one instance and refitting it would be fine for sklearn but invites subtle state carry-over, and makes it impossible for an arm to vary its construction per fold.
ddof=1 The sample SD across fits. §5.6's "do not bold a difference under one fold-SD" rule needs the spread of the fits, not the precision of their mean. Reporting the standard error instead — which is SD/√25, five times smaller — would make almost every null result look significant. oof_sum / oof_n accumulators In 5-fold CV every row is in exactly one validation fold, so oof_n is all ones and the division is a no-op. In repeated 5×5 CV every row appears five times, so the vector is the mean of five out-of-fold predictions. Dividing by the count handles both without branching, and the resulting vector is what the threshold is frozen from (§9.3).
Metrics computed per fold, then averaged Not pooled. Pooling all predictions and computing one AUC gives a slightly different number and, critically, no SD at all. The per-fold route is what makes a variance claim possible.

15.7 costs.py and metrics.py — decisions and evidence

These two are separated on purpose, and the boundary is meaningful rather than cosmetic: costs.py chooses things, metrics.py measures things. A function that does both is a function that can tune a threshold against the data it is scoring, which is §5.5's fatal flaw.

src/costs.pyexcerpt
def elkan_p_star(r):
    """Elkan (2001) cost-optimal decision threshold for a calibrated classifier.

    Acting is optimal when p * C_FN > (1 - p) * C_FP, i.e. p > 1 / (1 + r).
    """
    return 1.0 / (1.0 + r)

def threshold_grid(n=THRESHOLD_GRID_N):
    # Open interval: tau=0 predicts everyone default, tau=1 nobody. Neither is a decision.
    return np.linspace(1e-4, 1 - 1e-4, n)

def pick_threshold_oof(y_oof, proba_oof, r=R_HEADLINE, ead=None, grid=None):
    """Choose the cost-minimising threshold on out-of-fold training predictions.

    The returned scalar is frozen and applied unchanged to the test set. Sweeping the
    threshold against test labels is the single most common fatal flaw in this task.
    """
    grid = threshold_grid() if grid is None else np.asarray(grid, dtype=float)
    costs = np.array([cost_at_threshold(y_oof, proba_oof, t, r=r, ead=ead) for t in grid])
    tau = float(grid[int(np.argmin(costs))])
    return tau, {"grid": grid.tolist(), "cost": costs.tolist(),
                 "min_cost": float(costs.min()), "tau": tau}

Three details carry weight.

The grid is open, not closed. np.linspace(1e-4, 1-1e-4, 501) rather than np.linspace(0, 1, 501). At τ = 0 everybody is flagged as a default, so FN = 0 and the cost is just the count of negatives; at τ = 1 nobody is flagged, so FP = 0 and the cost is r × positives. Both are finite numbers that argmin will happily return if the cost ratio is extreme enough, and both are degenerate — "approve nobody" is not a credit policy. Excluding the endpoints means the returned τ is always a genuine decision rule, and it is why verify.py can assert 0 < τ < 1 as a hard invariant.

The function returns a tuple, and the first element is a scalar. float(grid[argmin]) — not an array, not a function of the data, not a slice. That scalar is written into the result JSON, read back by exp14, and applied to the test set unchanged. The second element is the whole swept curve, serialised so that §9's figures and this guide's interactive threshold explorer can be rebuilt from the committed result without refitting anything.

The same function serves both costing schemes. Passing ead=LIMIT_BAL switches from "every error costs the same" to per-client exposure weighting, and the dispatch lives in one if:

Two small things that prevent large errors

labels=[0, 1] is not decoration. Without it, confusion_matrix infers the label set from what it observes, so a subgroup in which the model flags nobody returns a 1×1 matrix and .ravel() raises a shape error — or worse, in a 2-element case, silently assigns the counts to the wrong variables. §13 evaluates small subgroups at a threshold of , so degenerate confusion matrices are a realistic occurrence, not a hypothetical.

And the decision is always (proba >= threshold), never model.predict(X). predict() hardcodes 0.5. Claiming a cost-optimised threshold of in the text while computing the confusion matrix with predict() is a specific, common, and completely invisible failure: the numbers look fine, they are just answering a different question than the prose says. The only defence is to never call predict() anywhere in the project, which is the convention here.

The - 2 * cov[0, 1] term is the entire reason DeLong exists. Two models scored on the same clients produce correlated ROC curves: a client who is obviously going to default is ranked highly by both. def paired_fold_test(deltas):

Arm-vs-arm comparisons cannot use DeLong, because the 25 repeated-CV folds are not an independent sample — every pair of training folds shares roughly 60% of its rows, so the per-fold differences are positively correlated, the computed SD is too small, and the p-value is too good. src/tuning.pyexcerpt
def make_objective(X, y, folds, spw=1.0, seed=SEED, space=None, model_fn=None):
    """`model_fn(params, spw, seed) -> estimator` lets each imbalance arm be tuned
    independently while sharing one search space and one objective."""
    if model_fn is None:
        def model_fn(params, spw, seed):
            return xgb_classifier(params, spw=spw, seed=seed)

    def objective(trial):
        params = suggest(trial, space)
        for k, (tr, va) in enumerate(folds):
            est = fit_one(model_fn(params, spw, seed), X.iloc[tr], y[tr], seed=seed)
            proba = est.predict_proba(X.iloc[va])[:, 1]
            aucs.append(roc_auc_score(y[va], proba))
            aps.append(average_precision_score(y[va], proba))
            # Report after each fold so MedianPruner can abandon hopeless trials early.
            trial.report(float(np.mean(aucs)), step=k)
            if trial.should_prune():
                raise optuna.TrialPruned()
        trial.set_user_attr("pr_auc_mean", float(np.mean(aps)))
        return float(np.mean(aucs))

15.9 The anatomy of one experiment

With the package doing the work, each experiment script is thin: it assembles components, and almost its only original content is the set of arms it defines and the notes it writes. exp03_imbalance is the most instructive because it touches nearly every module.

Six stages, in execution order. Each shows the real lines and the invariant that stage is responsible for. The point of the exercise is that no stage trusts the next one — each enforces its own contract and fails loudly rather than degrading quietly.

What the thinness is worth

Count what exp03 actually decides for itself: the four arm definitions, the trimmed SMOTE trial budget (SMOTE_TRIALS = 60, with the comment "each trial resamples to ~2x rows, so the budget is trimmed"), and the notes text. Everything else — the folds, the fitting, the early-stopping slice, the metric definitions, the SD convention, the threshold search, the JSON schema — comes from the package and is therefore identical to what exp01 and exp14 used. That is what makes the ladder table in §6 and the imbalance table in §8 directly comparable: not care, but shared code.

Why does exp03 tune arms C and D with their own Optuna studies instead of reusing arm A's parameters at a different scale_pos_weight?

Because reusing A's parameters would confound the thing being measured. The question is "does reweighting help?", and the fair version of that question is "does the best achievable reweighted model beat the best achievable unweighted model?" If you took parameters tuned for spw=1 and simply switched spw to , any underperformance could be dismissed as "you did not re-tune for it" — and legitimately so, since reweighting changes the gradient and Hessian magnitudes and therefore interacts with min_child_weight, reg_lambda and eta.

Giving each arm its own study removes that objection, at a cost of roughly tripling the experiment's runtime. The finding that reweighting buys nothing in ranking (§8) is then a statement about the strategy rather than about one unlucky parameter transplant — which is precisely why scale_pos_weight is excluded from the search space and fixed per arm instead (§7.3). The two decisions are the same decision seen from two directions.

Suppose you deleted require_artifact and made every experiment re-tune when best_params.json was missing. Name a concrete way the report could then become internally inconsistent.

Here is one path. You run exp02 and get a tuned configuration. You then run exp06 (feature groups), which finds best_params.json present and uses it. Later you delete artifacts/ to reclaim disk space, or move to another machine, and run exp11 (SHAP) — which, under the hypothetical, silently re-tunes. TPE is seeded, but it is tuning inside a different script that may pass a different feature set, a different spw, or simply a different number of trials. You now have two different "tuned XGBoost" models in the project.

The report then says "the tuned model achieves ROC-AUC X (§6) and its most important feature is Y with mean|SHAP| Z (§11)", and those two sentences describe different models. Nothing errors, no number looks implausible, and the inconsistency is undetectable from the outputs alone — the SHAP values are perfectly valid, just for a model that appears nowhere else. Exiting with "MISSING ARTIFACT … Produced by WP6. Run that first." turns an invisible inconsistency into a thirty-second inconvenience.

15.10 report.py and aggregate.py — reading the numbers back out

Rule 2's other half. These modules never fit anything; they only read results/. That one-way flow is what makes the claim "every number in the report traces to a committed result file" structurally true rather than aspirational.

That last clause is a genuinely useful trick and worth restating. Every cell that reports a cross-validated metric is formatted as mean ± SD at a fixed precision:

src/report.pyexcerpt
def pm(mean, sd, digits=4):
    if mean is None:
        return "--"
    if sd is None:
        return f"{mean:.{digits}f}"
    return f"{mean:.{digits}f} +/- {sd:.{digits}f}"

def num(value, spec=".4f"):
    """Format a metric, or `--` when it is null.

    The section 3.2 schema requires an inapplicable metric to be null rather than zero, so
    every table cell has to tolerate one. Rung 1b, for instance, scores `PAY_0` as an ordinal
    rather than fitting a model, so it has no accuracy at a 0.5 threshold.
    """
    return "--" if value is None else format(value, spec)

Because the SD is printed beside the mean in every table, a reader can perform the one-SD test themselves on any row pair without being told the answer. There is no table in the project where a mean appears alone. That is a formatting decision doing ethical work: the easiest way to oversell a 0.002 AUC win is to print the means in a tidy column and leave the variance in a footnote.

16.2 The two research questions, in one sentence each

Q1 — "Does the marginal performance gain achieved by ensemble architectures and non-linear models justify the corresponding loss in direct rule-based interpretability?"

Partly, and the ladder says exactly how much: going from one readable rule on PAY_0 to a tuned 23-feature gradient-boosted ensemble buys ROC-AUC — statistically unambiguous (DeLong p ) and operationally material at a 6:1 cost ratio, but most of it is bought by breadth rather than by non-linearity ( from giving a linear model all 23 features, against for the move to trees and for boosting over bagging) — so the gain is real, it is modest, it is mostly not where the interpretability was spent, and whether it justifies the loss depends entirely on whether Q2's answer holds.

Q2 — "Can post-hoc explainability techniques bridge this gap by providing regulatory-compliant decision auditability for non-linear ensemble models?"

For individual decisions, yes, with three stated limits. TreeSHAP gives an exactly additive log-odds decomposition per client (max additivity error ), the global ranking is stable under reseeding (top-10 Jaccard , Spearman ), and it independently reproduces the Phase 1 PAY_0 gradient from the model's internals (ρ ) — which is convergent validation, not circularity. The three limits: the collinear BILL_AMT block (VIF 13.9–25.7) must be read as a group because credit is split arbitrarily within it; SHAP explains the model, not causation; and the five importance measures disagree sharply (§12.3), so "feature importance" is not a well-defined quantity you can simply report.

16.3 Questions about the method

Walk me through every place a threshold could leak, and what stops it.

Three places, and they are worth naming in order because the first is the one people actually get wrong.

One: sweeping τ against test labels. You compute test probabilities, try 501 thresholds, pick the one minimising test cost, and report it. The resulting cost is optimistically biased by an amount nobody can estimate, and the operating point is unachievable in deployment because you will not have next quarter's labels. Stopped by pick_threshold_oof (§15.7), which only ever receives out-of-fold training predictions, and by metrics.evaluate taking the threshold as a required input and never searching for one.

Two: sweeping τ on in-fold training predictions. Subtler and still wrong — the model has partly memorised those rows, so its probability distribution there is sharper than on unseen data and the cost-minimising τ sits in the wrong place. Stopped by using cv_evaluate's out-of-fold vector: every prediction in it was made by a model that did not see that row.

Three: using model.predict(). Not leakage exactly, but the same class of error — it hardcodes 0.5, so the text claims an optimised threshold of while the confusion matrix reflects 0.5. Stopped by convention: predict() is never called anywhere in the project, only predict_proba(X)[:, 1] >= tau.

And the invariant that ties it together: the chosen τ is a frozen scalar, written into the result JSON, asserted by verify.py to lie strictly inside (0, 1), and applied unchanged to the test set exactly once.

Why ROC-AUC as the tuning objective on an imbalanced problem? Isn't PR-AUC the standard advice?

The standard advice is aimed at a different situation than this one. Three reasons, in order of weight.

Comparability across the ladder. ROC-AUC is prevalence-independent; PR-AUC is not — its baseline is the positive rate itself. The complexity ladder compares seven models including a majority-class classifier and a single rule, and is the answer to research question 1. An objective whose scale shifts with prevalence would make that comparison harder to read for no gain, since prevalence is fixed here anyway.

Variance. PR-AUC is noisier across folds because it is dominated by the ranking of a few hundred positives in each validation fold. Optimising a noisier objective over 150 trials means more of the selection is chasing fold noise. With a nearly flat objective surface — the whole completed-trial range spans against a pooled fold-SD of — that matters more than usual.

It is the declared primary metric in the credit-scoring benchmark literature (Lessmann et al., 2015), so it is the number comparable to published work.

The crucial qualifier: 22% is not severe imbalance. The PR-AUC advice is sharpest at 1:1000, where ROC-AUC can look excellent while the model is useless in the operating region. At roughly 1:3.5 both metrics see broadly the same thing. And PR-AUC was not ignored — it is logged every trial via set_user_attr and reported in every table. If the two had disagreed about arm ordering, that disagreement would itself have been a finding; they did not.

You excluded scale_pos_weight from the search space. Isn't that just refusing to tune an important hyperparameter?

It would be, if the objective could see it. It cannot, and that is the whole argument.

ROC-AUC depends only on the ranking of the scores. Reweighting the positive class rescales the gradients and shifts the predicted probabilities upward, but to a first approximation it applies a monotone transformation to the scores — and a monotone transformation leaves every pairwise ordering, and therefore ROC-AUC, essentially unchanged. So a tuner maximising ROC-AUC sees a flat direction in scale_pos_weight and picks whatever value happened to co-occur with a lucky draw on the other eight dimensions. The selected value would then be noise with the appearance of a tuned result, and — worse — it would be confounded with the other eight parameters, so the imbalance comparison in §8 could not be read as a comparison of strategies.

Fixing it per arm and tuning each arm independently converts it from a confound into a controlled factor. The empirical payoff: ROC-AUC across arms A, B and C moves by , well inside one fold-SD, while Brier degrades measurably ( → ). That is the mechanistic result — reweighting and threshold-moving are two parameterisations of the same decision shift, but only threshold-moving preserves probability semantics, and the cost analysis consumes probabilities. You cannot make that argument if the tuner has already scrambled the comparison.

Why is a SMOTE row rejected on semantic grounds rather than just because it scored worse?

Because "it scored worse" is a weak reason that invites the obvious rebuttal — tune it harder, try BorderlineSMOTE, try ADASYN. The semantic objection is not about performance and does not go away with more tuning.

SMOTE interpolates between a minority point and one of its neighbours, so a synthetic client gets PAY_0 = 0.37. There is no such repayment code. The scale is {−2 dormant, −1 paid in full, 0 revolving, 1…8 months delinquent}, Phase 1 established the default-rate response across it is non-monotonic (12.8% → 16.8% → 34.0% → 69.2%), and a value of 0.37 is not "between" 0 and 1 in any meaningful sense — it is a client who is simultaneously revolving and one month late. SMOTE's linear-interpolation assumption requires a metric space in which the straight line between two valid points contains valid points, and six of the twenty-three columns do not have that property.

The correct move, which is what was done, is to run the arm anyway and report the row — it comes in at ROC-AUC with Brier — and then reject it on the argument rather than the number. An empirical row plus a mechanistic reason is much stronger than either alone. And it keeps you honest: if SMOTE had won clearly, you would owe the reader an explanation of why a semantically invalid augmentation helped, which would itself be interesting.

Why de-duplicate before splitting rather than after, and how much did it matter?

It has to be before, and the reason is not subtle once stated: if 56 rows have identical feature vectors and the split happens afterwards, some copies land in train and some in test. The model then scores those test rows correctly by memory rather than by generalisation, and every metric in the project is inflated — not by a lot, but by an amount you cannot estimate and cannot remove after the fact.

It removed 56 rows (30,000 → ), so the direct effect here is small. Two things make it worth stating anyway. First, the magnitude is only knowable because it was checked; "it was probably fine" is not a result. Second, it had a downstream consequence that was not anticipated: §14.6 planned to quantify a Bayes-floor contribution from contradictory duplicate groups — identical features with opposite labels — and found of them, because de-duplication had already removed every such group. So the planned label-noise argument was abandoned and replaced with the feature-set-ceiling argument, which rests on the learning curve and the small tuning gain instead. Worth volunteering, because an argument you dropped for a stated reason reads much better than one that quietly disappeared.

16.4 Questions about the results

Your tuning gain is tiny. Doesn't that mean the tuning was a waste of time, or done badly?

It is over library defaults, which is of the same order as the pooled fold-SD of . So the honest statement is that tuning bought little in ranking, and no amount of presentation should dress that up.

But "waste of time" conflates two things. First, the search is evidence: the completed-trial range spans , so the flatness is a measured property of the objective surface on this data, not a failure to look. Second, and more useful — the small gain is itself a load-bearing piece of evidence for the ceiling argument. If this were an under-fitting problem, 150 TPE trials across eight dimensions would have found substantially more. Combined with the learning curve having plateaued by of the training data (§10.4), the natural reading is that the binding constraint is the feature set, not the model or its configuration. A six-month billing snapshot cannot observe job loss, illness or an income shock, and those are what actually cause a large share of defaults.

Tuning also bought two things that are not ROC-AUC: a model with trees rather than an untrimmed default, and — because early stopping and the regularisation terms were searched together — a configuration whose calibration is good enough for the cost analysis to be meaningful. The headline metric is not the only output.

Your model amplifies the demographic disparity that already exists in the data. Why is that in the report at all?

Because Phase 1 promised it. §2.2 of the proposal said quantifying the baseline disparities before modelling "is what makes a later fairness check interpretable rather than merely alarming", and a promised check that returns an uncomfortable answer and then vanishes is the single most damaging thing a report can do to its own credibility.

The result, precisely: the observed default-rate gap by SEX is percentage points in the data; the model's flag-rate gap at the frozen threshold is , so the ratio of model gap to data gap is — it amplifies. Three qualifications belong in the same breath. Ranking quality is near-parity (SEX ROC-AUC gap ), so the model is roughly equally good at ordering within each group; the four-fifths selection-rate ratio is ; and the amplification follows mechanically from thresholding a monotone score at a single global τ when the underlying distributions differ — it is not evidence of a discriminatory feature.

And then the result that makes the section worth the space. Removing all four demographic columns removes only of the SEX flag-rate gap: survives, reconstructed from the financial columns, at a cost of ROC-AUC. That is fairness-through-unawareness failing empirically on this dataset, which is exactly what Barocas & Selbst (2016) — already cited in the proposal — predicts. "We did not use gender" is therefore a claim about inputs, not about behaviour. That is a finding, and it is the kind of finding the Summary section rewards.

Your most important feature has a documented data irregularity. Should the headline result be trusted?

Say the irregularity first, in full. Repayment code 1 — one month delinquent — occurs 0, 0, 2, 4 and 28 times in April through August, and then 3,688 times in September. A behavioural variable does not change by three orders of magnitude in one month. The overwhelmingly likely explanation is that PAY_0 was constructed or snapshotted differently from the five historical columns, and PAY_0 is the most predictive variable in the dataset by a wide margin — mean|SHAP| , which is of total attribution.

So the ablation was run. Dropping PAY_0 entirely costs ROC-AUC in cross-validation ( → ) and on the test set. Two readings, both worth stating: the model is not a PAY_0 lookup table, since it retains most of its performance without it; and the remaining five PAY_n columns carry substantially overlapping information, which is consistent with the recency gradient Phase 1 measured.

The defensible conclusion is conditional rather than absolute. If the irregularity reflects a genuine September policy or reporting change, the headline holds for data collected the same way and would degrade on data collected differently — which is a deployment-monitoring requirement, not a flaw in the analysis. Reporting this earns more than hiding it would, and the alternative is indefensible: a marker who finds an unmentioned 3,688-vs-28 discontinuity in your top feature will reasonably assume you did not look.

Which single figure would you put in front of someone who had five minutes, and why?

The PAY_0 SHAP dependence plot, coloured by PAY_2.

It does four things at once. It shows the model learned a non-monotonic response — attribution dips at −1 and 0, then jumps sharply at 1 and 2 — which is the thing a linear model structurally cannot represent and is therefore the mechanism behind the non-linearity gain in §6. It reproduces the Phase 1 EDA gradient (12.8% → 16.8% → 34.0% → 69.2%) from the model's internals, at rank correlation against the observed rates — convergent validation from two independent directions, EDA and post-hoc explanation, which is much stronger than either alone. Final self-check: name the one thing in this project that, if it were wrong, would invalidate the most downstream results — and how you know it is not wrong.

artifacts/splits.npz. Every cross-validated number, every out-of-fold threshold, every SHAP value and the entire test-set evaluation are computed against those four index arrays.
