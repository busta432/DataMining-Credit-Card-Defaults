Section 15The implementation: reading the code

Everything up to here has been why. This section is where — which file holds which decision, what each layer guarantees, and which three or four lines are load-bearing enough that changing them would invalidate a result. The brief asks for core functions and code in the Solution section, so this doubles as the source for that half of the write-up: the excerpts below are the real ones, copied out of the repository, not illustrative pseudocode.

15.1 Why a package and not a notebook

Phase 1 was a notebook, and that was the right shape for it: 49 cells of exploration read top-to-bottom as an argument. Phase 2 is fourteen experiments totalling a couple of hours of compute, and a notebook is the wrong container for that for four independent reasons.

Problem with one notebookConsequenceWhat the package does instead
A single .ipynb is one JSON file with one linear cell list Two people — or two agents — editing different experiments produce a merge conflict in a machine-generated file that is painful to resolve by hand One module per concern, one script per experiment. Conflicts localise.
A kernel holds state in memory A crash at experiment 11 loses the first ten. "Restart and run all" costs the full 2–4 hours. Each script is standalone and idempotent; results persist to results/ as JSON the moment they exist.
Expensive intermediates live in variables Fourteen experiments refit the same tuned model fourteen times artifacts/ caches splits, best parameters, the fitted booster and the out-of-fold probability vectors. Each is written once.
A notebook's appendix listing is cell-order spaghetti The marker reads 3,000 lines of interleaved narrative and code with no structure The appendix lists twelve named modules with docstrings. It reads like software.

The notebook did not disappear — phase2_xgboost.ipynb still exists and still carries the narrative. It just does no heavy work. It reads results/ and renders, and it executes in well under a minute from a cold kernel. That inversion is the whole architectural idea: the notebook became a report generator and the package became the experiment.

15.2 The layers, and the two rules that hold them together

Nine modules in src/, fourteen scripts plus three utilities in experiments/, and a strict direction of dependency: scripts import the package, the package never imports a script.

1
config.py — constants only. No imports from the rest of the package, so nothing can create a circular dependency and every other module can read it freely.
2
data.py — loading, cleaning, engineering, splitting. Owns the train/test boundary.
3
models.py — every estimator in the project is constructed here and nowhere else.
4
runner.py — the one cross-validation loop, plus the result-file writer.
5
costs.py, metrics.py, tuning.py — decisions, evidence, and search respectively.
6
experiments/exp01…exp14 — thin. Each one assembles components and writes JSON. Almost no logic of its own.
7
report.py, figures.py, aggregate.py, verify.py — read results/ back out. These never fit a model.
Rule 1 — there is exactly one evaluation path

Every experiment that reports a cross-validated number calls runner.cv_evaluate(). None implements its own loop. This is not a style preference. Divergent CV loops are the single largest source of numbers that cannot be reconciled later: one loop shuffles, another does not; one computes the mean of per-fold AUCs, another pools predictions and computes one AUC; one carves an early-stopping slice, another leaks the validation fold into it. All four produce plausible-looking ROC-AUCs that differ in the third decimal, and six weeks later nobody can say which table used which. One function means the comparison across all fourteen experiments is definitionally like-for-like.

Rule 2 — no number is ever retyped. Experiments write JSON; report.py and figures.py read it back. The report quotes results/manifest.csv. This very guide is built the same way — see §15.12. A number that appears in prose but not in a committed result file is, by construction, impossible.

Two things in that excerpt are worth defending out loud, because a marker may read them as arbitrary.

Why CV_SEED = 7 rather than reusing 42

The tuner optimised against the five folds generated with random_state=SEED. If the variance-reporting folds were generated from the same seed, the first repeat of the repeated-CV would be identical to the folds Optuna selected against — and the reported mean ± SD would be partly a measurement of how well the tuner overfitted its own folds rather than of genuine fold-to-fold variance. Using a distinct integer decorrelates them. It costs nothing and it removes a question the reader would otherwise be right to ask. (§5.3 has the full argument; this is where it is actually implemented, in one integer.)

The library incompatibility that forced a pinned flag

This one is real, current, and cost debugging time, so it is worth stating precisely.

src/config.pyexcerpt
# enable_categorical defaults to True in xgboost 3.4, and shap 0.52 reads that flag
# alone to decide a model has categorical splits -- which blocks interventional
# TreeSHAP. Numeric models must set it False explicitly. See SETUP.md.
XGB_FIXED = {
    "tree_method": "hist",
    "enable_categorical": False,
    "eval_metric": "auc",
    "n_jobs": -1,
    "random_state": SEED,
}

Read the chain carefully. xgboost flipped enable_categorical to default True. That is harmless on its own — with no category-dtype columns the flag changes nothing about the fit. But shap inspects that constructor flag, not the actual dtypes, to decide whether the booster might contain categorical splits; if the flag is set it refuses to run interventional TreeSHAP, because the interventional algorithm would have to resample a categorical level it cannot reason about. So a numeric model, trained on integer columns, silently loses access to the explainer configuration §11.4 argues for — not because of anything about the model, but because of a default in one library read by a guard in another. Pinning the flag False in XGB_FIXED fixes it for every estimator in the project at once, which is the payoff of constructing all of them in one place. The one arm that genuinely wants categorical handling — the enable_categorical row of the encoding ablation (§10.1) — passes it explicitly as an argument, and that arm does not need SHAP.

The documented deviation

The plan budgeted 60–80 Optuna trials against an estimated 20–40 minutes. The comment in config.py records what happened instead:

15.4 data.py — where the leakage firewall lives

This is the most consequential module in the project, because every protection described in §5 is ultimately one of its functions. It has four jobs in sequence.

(a) Load and clean, with the Phase 1 assertions carried across intact

src/data.pyexcerpt
def clean(raw):

    De-duplication happens before any split, so identical feature-rows cannot straddle
    train and test and inflate every score.

    assert int(df[TARGET].sum()) == 6622, "Unexpected default count after cleaning"
    assert set(df["EDUCATION"].unique()) <= {1, 2, 3, 4}, "EDUCATION outside documented domain"
    assert set(df["MARRIAGE"].unique()) <= {1, 2, 3}, "MARRIAGE outside documented domain"

Six assertions, ported verbatim from Phase 1, and the reason they are assertions rather than printed summaries is that they are claims the report makes. The report says Phase 2 operates on the same -row frame the proposal described. That sentence is either true or the module refuses to import. There is no third state in which the number drifted and nobody noticed.

Note also the ordering, which §5.1 argues for and this function enforces: drop_duplicates runs before anything else and before any split exists. Twenty-four identical feature rows split across train and test would let a model score them correctly by memory and inflate every metric in the project. De-duplicating first makes that structurally impossible rather than merely unlikely.

(b) Engineer, with an explicit missing-value convention

§10.2 benchmarks the derived features; here is how they are built, and the one subtlety is the divide-by-zero guard.

src/data.pyexcerpt
# Evenly spaced chronological month index; the OLS slope denominator is therefore
# a constant and the whole trend reduces to one dot product.
_X_MONTH = np.arange(6, dtype=float)
_X_CENTRED = _X_MONTH - _X_MONTH.mean()
_X_SS = float((_X_CENTRED**2).sum())  # 17.5

def _ols_slope(values):
    """Least-squares slope of each row against the chronological month index."""
    v = np.asarray(values, dtype=float)
    return (v - v.mean(axis=1, keepdims=True)) @ _X_CENTRED / _X_SS

# ... inside engineer():
# Index-aligned with the bill of the same month, matching the column naming.
safe_bills = np.where(bills > 0, bills, np.nan)
ratios = pays / safe_bills

Why NaN and not a sentinel like -999 or 0

1,930 rows carry a negative BILL_AMT (Phase 1 §1.6) and many more carry exactly zero, so PAY_AMT / BILL_AMT is genuinely undefined for a substantial minority of clients — it is not a data error to be patched. Three options: fill with zero, fill with a sentinel, or emit NaN. Filling with zero lies: it asserts the client repaid nothing when in fact there was nothing to repay, and it places them next to genuine non-payers in the ordering. A sentinel like -999 is honest but forces the tree to spend a split separating the sentinel from the real values, and that split consumes depth. The NaN route is strictly better for this learner: XGBoost's sparsity-aware split finding (§3.6) learns a default direction for missing values at every node, at no cost in depth, choosing whichever side reduces loss more. So the undefined-ness is carried as information rather than destroyed. The isinf assertion then guarantees the guard actually worked — a division that slipped through as inf would propagate silently into the histogram builder.

The slope trick is a small thing worth noticing. Because the six months are evenly spaced, the denominator Σ(x−x̄)² is the constant 17.5 for every client, so the per-client OLS slope collapses to a single matrix–vector product rather than 29,944 calls to a regression routine. It is the difference between a few milliseconds and a few seconds, and more importantly it is one line that is obviously correct.

(c) Split once, cache, and never reshuffle

    Written once by WP4 and read by every experiment, so all fourteen share identical

    """

The output is artifacts/splits.npz holding four integer arrays: train_idx (), test_idx (), fold_id for the five selection folds, and rep_fold_id, a 5×23,955 matrix for the twenty-five variance folds. Fold membership is stored as an id per row rather than as lists of indices, which is compact and makes the "does this partition the training rows exactly once?" check in verify.py trivial.

Caching is not an optimisation here, it is a correctness mechanism. If each experiment called train_test_split itself, then a single accidental change — a different random_state, a forgotten stratify=, an experiment run before a cleaning fix and another after — would produce two different hold-out sets, and two experiments' numbers would no longer be comparable while looking entirely normal. One cached file eliminates the whole class of error.

(d) The firewall itself: two context functions, one of which cannot return test rows

This is the part that makes §5.7's leakage audit a one-line grep rather than a careful reading of 2,000 lines.

Why this design beats "just be careful"

An experiment that calls training_context() has no reference to a test row anywhere in its scope. Not a filtered-out one, not a commented-one — the held-out rows simply do not exist in any variable the script can reach. Leaking therefore requires importing a different function, which is a visible, greppable, single-token act. Compare the alternative, where every script holds X_train, X_test, y_train, y_test and correctness depends on nobody ever typing the wrong one of four nearly-identical names across 2,000 lines while tired. The firewall converts a discipline problem into a type-system-shaped problem, and then verify.py checks it mechanically (§15.11). Note the honest framing in the docstring too: SHAP is licensed on the hold-out because it explains held-out decisions and selects nothing — an explanation cannot leak into a choice that was already frozen.

15.5 models.py — every estimator, constructed once

Nothing in experiments/ ever calls XGBClassifier(...). All eleven estimator varieties — the seven ladder rungs, the three encoding arms, the SMOTE wrapper — are built by factory functions here, so a configuration cannot drift between two experiments that believe they are testing the same model.

src/models.pyexcerpt
def xgb_classifier(params=None, spw=1.0, early_stopping=True,
                   enable_categorical=False, seed=SEED):
    """XGBoost with the project's fixed infrastructure settings.

    `early_stopping_rounds` and `eval_metric` go in the constructor, not `.fit()` --
    the XGBoost 2.x/3.x API moved them. `enable_categorical` is pinned False because
    xgboost 3.4 defaults it True and shap then refuses interventional TreeSHAP.
    """
    p = dict(XGB_FIXED)
    p["enable_categorical"] = enable_categorical
    p["random_state"] = seed
    p["scale_pos_weight"] = spw
    if early_stopping:
        p["n_estimators"] = N_ESTIMATORS_CAP
        p["early_stopping_rounds"] = ES_ROUNDS
    if params:
        p.update(params)
    return XGBClassifier(**p)
The API trap that silently does nothing

Almost every tutorial written before 2023 shows model.fit(X, y, early_stopping_rounds=50, eval_metric="auc"). In the XGBoost 2.x and 3.x scikit-learn API those two arguments moved to the constructor. Passing them to .fit() now raises a TypeError — which is the good outcome, because you find out immediately. The dangerous variant is omitting them entirely and assuming the n_estimators=2000 cap is being trimmed by early stopping when it is not: you then train two thousand trees on 24,000 rows, overfit substantially, and the only symptom is a mysteriously large train/CV gap. Note also what the early_stopping=True branch does — it sets n_estimators to the cap only when early stopping is active. Rung 5, the library-defaults rung, deliberately gets neither, because its entire purpose is to measure what you get with no tuning and no stopping at all.

The ladder's interpretability-cost column is computed, not asserted

src/models.pyexcerpt
def count_tree_nodes(fitted):
    """Interpretability cost for the tree rungs: nodes a human must read."""
    est = fitted.best_estimator_ if isinstance(fitted, GridSearchCV) else fitted
    if isinstance(est, DecisionTreeClassifier):
        return int(est.tree_.node_count)
    if isinstance(est, RandomForestClassifier):
        return int(sum(t.tree_.node_count for t in est.estimators_))
    if isinstance(est, XGBClassifier):
        return int(len(est.get_booster().get_dump()))
    return None

This is the function behind §6.2's claim that the accuracy/interpretability trade-off is a measured axis rather than an assertion — and it is also the source of the unit inconsistency §6.2 flags honestly: the sklearn branches return node counts while the XGBoost branch returns len(get_dump()), which is a tree count. Both are "things a human must read", but they are not the same unit, so the column must be read as an order of magnitude and not a ratio. Better to say that than to quietly present 692,674 and 499 as comparable.

The one custom estimator, and the one place it deliberately departs from the obvious design

src/models.pyexcerpt
class SmoteXGB(BaseEstimator, ClassifierMixin):
    """SMOTE + XGBoost, resampling strictly inside `fit`.

    Equivalent to an imblearn Pipeline for leakage purposes -- oversampling only ever
    sees the rows passed to `fit`, which cv_evaluate restricts to the fold's training
    half -- with one deliberate refinement: the early-stopping slice is carved off
    *before* resampling, so it retains the natural 22% prevalence. Validating against
    synthetically balanced data would make the stopping criterion measure the wrong
    distribution.
    """
    def fit(self, X, y):
        y = np.asarray(y).astype(int)
        i_fit, i_es = train_test_split(
            np.arange(len(y)), test_size=ES_SLICE, stratify=y, random_state=self.seed
        )
        X_res, y_res = SMOTE(random_state=self.seed).fit_resample(
            X.iloc[i_fit], y[i_fit]
        )
        self.model_ = xgb_classifier(self.params, spw=1.0, seed=self.seed)
        self.model_.fit(X_res, y_res,
                        eval_set=[(X.iloc[i_es], y[i_es])], verbose=False)
        self.classes_ = np.array([0, 1])
        return self
Why not simply imblearn.Pipeline([("smote", SMOTE()), ("xgb", ...)])

The pipeline is the standard answer and it is correct on the question everyone worries about: it resamples inside fit only, so synthetic minority rows never reach a validation fold, and the notorious failure of SMOTE-before-split is avoided. §8.5 explains why that failure is so severe — interpolating before splitting places synthetic points between a train row and a test row, and the model can then almost memorise the test set.

But the pipeline gets one secondary thing wrong here. XGBoost needs an early-stopping eval_set, and if that slice is taken from the pipeline's output it is 50/50 balanced synthetic data. Early stopping would then be minimising AUC against a distribution that does not exist, and would stop at the wrong tree count — not catastrophically, but wrongly, and in a way that would make arm D's comparison against A/B/C unfair. Carving i_es out first, at the natural prevalence, and resampling only i_fit, fixes it. This is the kind of detail that justifies writing twenty lines of custom estimator instead of using the one-liner: the one-liner is leakage-safe but distribution-wrong, and only one of those two is obvious.

15.6 runner.py — the single evaluation path

Rule 1 made concrete. Four functions matter.

fit_one — where the early-stopping slice is carved

src/runner.pyexcerpt
def fit_one(est, X_tr, y_tr, seed=SEED):
    """Fit a single estimator, carving the early-stopping slice out of the training data.

    The eval_set comes from an inner slice of this fold's *training* rows, so the outer
    validation fold is never seen by early stopping and the test set never at all.
    """
    if _uses_early_stopping(est):
        i_fit, i_es = train_test_split(
            np.arange(len(y_tr)), test_size=ES_SLICE, stratify=y_tr, random_state=seed
        )
        est.fit(X_tr.iloc[i_fit], y_tr[i_fit],
                eval_set=[(X_tr.iloc[i_es], y_tr[i_es])], verbose=False)
    else:
        est.fit(X_tr, y_tr)
    return est

Nine lines, and they are the implementation of §5.4. The arguments are already restricted to one fold's training half by the caller; fit_one splits that half again, 85/15, and uses the 15% purely to decide when to stop adding trees. Three distinct row sets are therefore in play per fold — fit rows, stopping rows, scoring rows — and each is used for exactly one purpose.

_uses_early_stopping is a two-line type check rather than a flag, which matters because the same function fits the dummy classifier, the logistic pipeline, the grid-searched tree, the random forest and the boosters. Non-XGBoost estimators take the else branch and get all the training rows, which is correct: handing a random forest an 85% subsample to match XGBoost would handicap it for no reason and corrupt the ladder comparison.

cv_evaluate — mean, SD, and the out-of-fold vector in one pass

src/runner.pyexcerpt
def cv_evaluate(X, y, factory, folds, seed=SEED, collect_oof=True, return_models=False):
    """Fit `factory()` on every fold and report mean +/- SD across fits.

    The SD returned is across fits, not the standard error -- it is the quantity the
    report uses to decide whether two arms are distinguishable.
    """
    for k, (tr, va) in enumerate(folds):
        est = fit_one(factory(), X.iloc[tr], y[tr], seed=seed)
        proba = est.predict_proba(X.iloc[va])[:, 1]
        per_fold.append(_fold_metrics(y[va], proba))
        if collect_oof:
            oof_sum[va] += proba
            oof_n[va] += 1
        ...
    for m in ("roc_auc", "pr_auc", "brier"):
        vals = np.array([f[m] for f in per_fold], dtype=float)
        summary[f"{m}_mean"] = float(vals.mean())
        summary[f"{m}_sd"] = float(vals.std(ddof=1)) if len(vals) > 1 else 0.0

Four design points, each of which shows up somewhere in the results.

DetailWhy it is that way
factory is a callable, not an estimator Calling factory() inside the loop builds a fresh estimator per fold. Passing one instance and refitting it would be fine for sklearn but invites subtle state carry-over, and makes it impossible for an arm to vary its construction per fold.
ddof=1 The sample SD across fits. §5.6's "do not bold a difference under one fold-SD" rule needs the spread of the fits, not the precision of their mean. Reporting the standard error instead — which is SD/√25, five times smaller — would make almost every null result look significant. This single keyword argument is the difference between an honest comparison and a misleading one.
oof_sum / oof_n accumulators In 5-fold CV every row is in exactly one validation fold, so oof_n is all ones and the division is a no-op. In repeated 5×5 CV every row appears five times, so the vector is the mean of five out-of-fold predictions. Dividing by the count handles both without branching, and the resulting vector is what the threshold is frozen from (§9.3).
Metrics computed per fold, then averaged Not pooled. Pooling all predictions and computing one AUC gives a slightly different number and, critically, no SD at all. The per-fold route is what makes a variance claim possible.

Three enforcement details

Null, never zero. Rung 1b scores PAY_0 as a raw ordinal rather than fitting a model, so it has no accuracy at a 0.5 threshold. Writing 0.0 there would be a false claim that it got nothing right, and it would plot as a bar at the origin. null propagates through report.num() to a dash in the table and is simply absent from the chart. The schema check in verify.py enforces the distinction.

notes is mandatory and the error message says what counts. Not an empty string, not a default. Every anomaly described in §6 through §14 — the seed-10 early-stopping outlier, the zero contradictory duplicate groups, the raised trial budget — is in a committed notes field because the writer refuses to run without one. A field you may skip is a field you will skip at 2am on the night an experiment finally works.

versions() is captured per run. Every result file records the Python, numpy, sklearn, xgboost, shap, optuna, imblearn and pandas versions that produced it. That is what lets §15.12 state the environment without anybody reading it off a terminal, and it is what would let a future reader tell whether a number changed because of a code edit or a library upgrade.

Nine experiments depend on artifacts/best_params.json. The tempting behaviour when it is missing is to re-tune — convenient, and catastrophic: the re-tune would run inside a different script with possibly different folds, and two experiments would then be reporting "the tuned model" while meaning two different models. Exiting with a message that names the script to run costs the user thirty seconds and preserves the invariant that there is one tuned configuration in the project.
