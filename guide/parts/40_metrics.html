Section 4Measuring honestly: what each metric can and cannot see

Every metric is a lossy summary. Pick the wrong one and a broken model looks excellent; pick one and report it alone and you will be unable to answer the obvious question in the viva. This section derives the four metrics the project reports — ROC-AUC, PR-AUC, Brier and ECE — from the confusion matrix, shows exactly what each is blind to, and demonstrates the blindness on your own numbers.

4.1 The accuracy trap, with the actual number

The dataset is defaulters. So a model that is a constant — predict "no default" for every single client, read no features at all — is right of the time.

Rung 0 exists to make this unarguable

The complexity ladder's first rung is DummyClassifier(strategy="most_frequent"). It scores accuracy and 0.0% recall: it catches zero defaulters. Its ROC-AUC is exactly 0.500, because a constant score cannot rank anybody above anybody else.

Compare the tuned model at the default threshold: accuracy. The tuned ensemble is four-tenths of a percentage point more accurate than a model that does nothing. If accuracy were the metric, the entire project would be worth 0.4 pp. It is the wrong metric — and the reason it is wrong is that it weights a missed default and a rejected good customer identically, which no lender does.

4.2 Everything is built from four counts

Fix a threshold τ. Flag client i if p̂ᵢ ≥ τ. Every classification metric in this project is a function of the resulting four counts — nothing else:

Predicted defaultPredicted no default
Actually defaulted TP — correctly flagged FN — missed default, costs LGD × EAD
Actually did not FP — rejected good customer, costs forgone NIM TN — correctly left alone
Recall (TPR, sensitivity) = TP / (TP + FN)  ·  Precision (PPV) = TP / (TP + FP)
FPR = FP / (FP + TN)  ·  Accuracy = (TP + TN) / n  ·  F1 = 2·P·R / (P + R)(7)
Recall
answers "of the clients who did default, what fraction did we flag?" — the lender's exposure question
Precision
answers "of the clients we flagged, what fraction really defaulted?" — the operational-burden question. It depends on prevalence; recall does not
FPR
the collateral-damage rate among good customers. ROC is built from (FPR, recall) because both are computed within one true class — which is exactly what makes ROC prevalence-independent
F1
the harmonic mean of precision and recall. The project reports it but never optimises it, because it silently asserts that a FP and a FN cost the same — and §9 derives that they differ by a factor of six

4.3 The threshold is a business decision, not a model parameter

This is the single most important conceptual separation in the project, so it gets stated twice. A trained classifier emits a score. Turning a score into an action requires a threshold. The model does not supply one — 0.5 is a default in the library, not a recommendation, and it is optimal only in the special case where a FP and a FN cost exactly the same.

Consequently the project evaluates ranking and calibration separately from the decision: ROC-AUC and Brier judge the score, and §9 chooses τ from a cost model. The widget below is the real out-of-fold sweep — move τ and watch which error you are buying.

Where the widget's numbers come from — and why it is not a re-run

results/exp10_cost.json stores, for each cost ratio, the swept threshold grid and the total cost at each point — but not the confusion matrix. Under the flat scheme, though, cost is exactly linear in the two error counts:

cost(r) = r·FN + FP(8)

Two ratios therefore give two equations in two unknowns, solvable in closed form:

FN = cost(2) − cost(1)     FP = 2·cost(1) − cost(2)(9)

The remaining four ratios (r = 5, 6, 10, 20) then over-determine the system. guide/build_guide.py does not discard them — it asserts that the recovered FN/FP reproduce all four curves to the last unit, and aborts the build otherwise. They do. So the matrix you are manipulating is the genuine out-of-fold one the report quotes, recovered from committed results rather than recomputed with a possibly-drifted seed.

A pleasant side effect: the endpoints confirm the split sizes. At τ → 0 nothing is missed, so FN = 0 and FP equals the entire negative class (); at τ → 1 nothing is flagged, so FN equals the entire positive class (). Those sum to — the training portion, exactly as §5 specifies.

4.4 ROC-AUC from first principles

Sweep τ from 1 down to 0. At each value plot (FPR, recall). The curve traced out is the ROC curve; the area under it is ROC-AUC. Two facts make it the project's primary metric, and both are worth being able to derive on demand.

Fact 1 — AUC is a probability, via Mann–Whitney

Draw one defaulter and one non-defaulter uniformly at random. Then

ROC-AUC = P( score(defaulter) > score(non-defaulter) ) + ½·P( tie )(10)

Sketch. Order all n clients by score. A threshold placed between two adjacent clients corresponds to one point on the ROC curve, and stepping past a positive moves the curve up by 1/P while stepping past a negative moves it right by 1/N. The area accumulated by one rightward step is (number of positives already above) / P × 1/N. Summing over all negatives counts every (positive, negative) pair in which the positive outranks the negative, divided by P·N — which is exactly the pair probability above. The AUC is the normalised Mann–Whitney U statistic.

Three consequences you should be able to state. (i) 0.5 is chance, because a random ranking wins half the pairs — which is why rung 0 scores exactly 0.500. (ii) AUC depends only on the order of the scores, so any strictly increasing transform of the scores leaves it unchanged. (iii) It is computed within classes, so it does not move when prevalence does.

Consequence (ii) is not a curiosity — it is the load-bearing argument for two separate design decisions in this project, and both appear in the report's Solution section.

The invariance does real work twice
  1. It is why scale_pos_weight is excluded from the tuning search space (§7). Reweighting the positive class rescales the logits roughly monotonically, so it barely moves the order — and therefore barely moves ROC-AUC. A tuner optimising ROC-AUC is nearly blind to the parameter and would pick a value arbitrarily, which turns the imbalance study into a confound. Fixing it per arm and tuning each arm separately makes it a controlled comparison instead.
  2. It is why ROC-AUC alone is insufficient and Brier is mandatory (§9). Calibration is a monotone-transform property, so ROC-AUC cannot see it at all. §4.6 shows this on your own two arms.
Fact 2 — why ROC-AUC and not PR-AUC as the tuning objective

Three reasons, in the order they would be defended:

  • Comparability across the ladder. Prevalence-independence means rung 1 and rung 6 are measured on the same scale even though the folds differ slightly in composition.
  • Lower fold-to-fold variance. PR-AUC's precision term has the small positive count in its denominator, so it is noisier. Across your 25 repeated-CV fits the tuned model's ROC-AUC SD is ; optimising a noisier objective means the tuner spends trials chasing fold noise.
  • Precedent. Lessmann et al. (2015) benchmark credit-scoring classifiers on ROC-AUC, so reporting it keeps the result comparable to published work.

PR-AUC is still logged every trial and reported in every table — it is simply not the thing being maximised. "Log it, report it, do not optimise it" is the defensible position; reporting only the metric you optimised is not.

4.5 PR-AUC, and why its baseline is not 0.5

The precision–recall curve plots precision against recall over the same threshold sweep. Its no-skill baseline is the prevalence, not 0.5: a random classifier flags a prevalence-sized fraction of defaulters at every recall, so its precision is flat at . That is exactly the rung-0 PR-AUC in your ladder () — the equality is a sanity check, not a coincidence.

Because precision has FP in its denominator and FP is drawn from the large class, PR-AUC is far more sensitive than ROC-AUC to performance in the high-threshold region where a lender actually operates. The ladder shows the two metrics telling the same qualitative story at different magnifications:

4.6 Brier score: the metric that sees what ROC-AUC cannot

The Brier score is the mean squared error of the probabilities themselves:

Brier = (1/n) Σᵢ (p̂ᵢ − yᵢ)²(11)

Lower is better. It is a strictly proper scoring rule: it is uniquely minimised by reporting your true believed probability, so you cannot improve it by shading your forecasts. And unlike ROC-AUC it is not invariant to monotone transforms — squash every probability toward 0.5 and the ranking is untouched while the Brier score degrades. That is exactly the sensitivity the project needs.

The decomposition that explains why

Murphy's decomposition splits the Brier score into three terms:

Brier = reliability − resolution + uncertainty(12)
reliability
(lower better) within each probability bin, the squared gap between the mean prediction and the observed rate — this is calibration error
resolution
(higher better) how far bin-wise observed rates spread away from the base rate — this is discrimination, the thing ROC-AUC measures
uncertainty
π(1 − π) at prevalence π; a property of the dataset, identical for every model, here

So Brier = discrimination and calibration in one number, which is both its strength and the reason the project also reports ECE: a single scalar cannot tell you which term moved.

4.7 Expected Calibration Error

Bin the predictions into B equal-width bins, and average the gap between predicted and observed within each, weighted by bin population:

ECE = Σb=1..B (nb/n) · | mean(p̂)b − rate(y)b |(13)

ECE is the reliability term of equation (12) made legible: an L1 average of vertical distances from the diagonal on a reliability diagram. The project uses B = 10.

Three honest caveats about ECE
  • It is bin-count-dependent. More bins means fewer clients per bin, noisier rates, usually a larger ECE. A quoted ECE is meaningless without its B.
  • It is not a proper scoring rule. A constant predictor that always outputs the base rate is perfectly calibrated and achieves ECE ≈ 0 while having zero discrimination. ECE must therefore always be read next to a discrimination metric — which is why the tables carry ROC-AUC, Brier and ECE together and never ECE alone.
  • Equal-width binning puts most clients in the first two bins at this prevalence, so the high-probability bins are sparse and their contribution is noisy. The reliability curves in §9 are plotted with their bin counts for exactly this reason.

4.9 Variance, and the rule that stops over-claiming

A single CV number is a point estimate with no error bar, and model-comparison claims made on point estimates are the most common failure in reports like this. So every metric in the project is reported as mean ± SD across 25 fits — RepeatedStratifiedKFold(n_splits=5, n_repeats=5), which is 5 independent 5-fold partitions of the training data.

Two deliberate choices in those four lines
  • random_state=7, not SEED=42. The tuner's folds use 42. If the variance-reporting folds reused 42 they would be the same partition the hyperparameters were selected on, and the reported SD would understate the true spread. A distinct seed decorrelates them.
  • ddof=1 and the name _sd. The reported figure is the sample standard deviation across fits, not the standard error of the mean. SEM = SD/√25 = SD/5 would look five times tighter and would be the wrong quantity: the question is "how much does this number move if I re-partition?", not "how precisely do I know its mean?".
The one-SD rule

Any gap smaller than roughly one fold-SD is reported as not distinguishable — stated in words, never bolded, never described as an improvement. The tuned model's SD is , so differences below about 0.007 ROC-AUC are noise. This rule is what makes the §8 imbalance result reportable as a mechanistic finding instead of a fabricated win.

Two further statistical points the project is careful about: (a) repeated-CV folds overlap, so a paired t-test across them is anti-conservative (Nadeau & Bengio, 2003) — the project notes this and leans on SD comparison instead; (b) DeLong's test is applied to exactly one comparison, tuned XGBoost against the PAY_0 baseline on the single held-out test set, because that is its actual use case: two correlated ROC curves on the same sample. Running it across CV folds would violate the independence its variance estimate assumes.

Self-check: someone reports "94% accuracy, up from 78%" — what do you ask?

What the recall is, and at what threshold. On this dataset 78% is the do-nothing constant, so the claim is that 16 pp of accuracy was gained — but accuracy can also be bought by making a model more conservative, which reduces recall. Then: what the cost assumption is, since accuracy weights a missed default and a rejected good customer identically. Finally: was the threshold 0.5, and was it chosen on the test set?

Self-check: two models have identical ROC-AUC to four decimals — can they behave differently?

Yes, in two distinct ways.

Calibration. ROC-AUC is invariant to monotone transforms, so one model's probabilities can be systematically inflated while its ranking is untouched. That is literally arms A and C in §4.6: indistinguishable ROC-AUC, Brier differing by .

Local ordering. Equal total area does not mean the same curve. One model can dominate at low FPR — where a lender actually operates — while the other catches up at high FPR and ends level. This is why PR-AUC and the operating-point confusion matrix are both reported rather than ROC-AUC alone.

Self-check: why is rung 0's PR-AUC equal to the prevalence while its ROC-AUC is exactly 0.5?

A constant score ranks nobody above anybody, so every randomly drawn (positive, negative) pair is a tie; by equation (10), AUC = ½ · P(tie) = ½ · 1 = 0.5.

For precision–recall, every threshold either flags everyone or nobody. When everyone is flagged, recall = 1 and precision = TP/(TP+FP) = prevalence. The curve is the horizontal line at precision = prevalence, so its area is the prevalence: = in the ladder JSON.
