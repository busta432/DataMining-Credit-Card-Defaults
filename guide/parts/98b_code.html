15.7 costs.py and metrics.py — decisions and evidence

These two are separated on purpose, and the boundary is meaningful rather than cosmetic: costs.py chooses things, metrics.py measures things. A function that does both is a function that can tune a threshold against the data it is scoring, which is §5.5's fatal flaw.

src/costs.pyexcerpt
def elkan_p_star(r):
    """Elkan (2001) cost-optimal decision threshold for a calibrated classifier.

    Acting is optimal when p * C_FN > (1 - p) * C_FP, i.e. p > 1 / (1 + r).
    """
    return 1.0 / (1.0 + r)

def threshold_grid(n=THRESHOLD_GRID_N):
    # Open interval: tau=0 predicts everyone default, tau=1 nobody. Neither is a decision.
    return np.linspace(1e-4, 1 - 1e-4, n)

def pick_threshold_oof(y_oof, proba_oof, r=R_HEADLINE, ead=None, grid=None):
    """Choose the cost-minimising threshold on out-of-fold training predictions.

    The returned scalar is frozen and applied unchanged to the test set. Sweeping the
    threshold against test labels is the single most common fatal flaw in this task.
    """
    grid = threshold_grid() if grid is None else np.asarray(grid, dtype=float)
    costs = np.array([cost_at_threshold(y_oof, proba_oof, t, r=r, ead=ead) for t in grid])
    tau = float(grid[int(np.argmin(costs))])
    return tau, {"grid": grid.tolist(), "cost": costs.tolist(),
                 "min_cost": float(costs.min()), "tau": tau}

Three details carry weight.

The grid is open, not closed. np.linspace(1e-4, 1-1e-4, 501) rather than np.linspace(0, 1, 501). At τ = 0 everybody is flagged as a default, so FN = 0 and the cost is just the count of negatives; at τ = 1 nobody is flagged, so FP = 0 and the cost is r × positives. Both are finite numbers that argmin will happily return if the cost ratio is extreme enough, and both are degenerate — "approve nobody" is not a credit policy. Excluding the endpoints means the returned τ is always a genuine decision rule, and it is why verify.py can assert 0 < τ < 1 as a hard invariant.

The function returns a tuple, and the first element is a scalar. float(grid[argmin]) — not an array, not a function of the data, not a slice. That scalar is written into the result JSON, read back by exp14, and applied to the test set unchanged. The second element is the whole swept curve, serialised so that §9's figures and this guide's interactive threshold explorer can be rebuilt from the committed result without refitting anything.

The same function serves both costing schemes. Passing ead=LIMIT_BAL switches from "every error costs the same" to per-client exposure weighting, and the dispatch lives in one if:

The flat scheme asks "what happens as the ratio varies?", so it must be parameterised by the ratio. The instance scheme asks "what is the dollar cost on this portfolio?", so it must use the two credit parameters the ratio was derived from. The fact that LGD/NIM = 's reciprocal reproduces the headline ratio is then a consistency check rather than a coincidence.

metrics.py — the function that refuses to choose a threshold

src/metrics.pyexcerpt
def evaluate(y_true, proba, threshold=0.5):
    """Ranking, calibration and thresholded-decision metrics for one prediction vector.

    `threshold` must already be frozen from out-of-fold data (see costs.pick_threshold_oof);
    this function never searches for one.
    """
    pred = (proba >= threshold).astype(int)
    tn, fp, fn, tp = confusion_matrix(y_true, pred, labels=[0, 1]).ravel()
Two small things that prevent large errors

labels=[0, 1] is not decoration. Without it, confusion_matrix infers the label set from what it observes, so a subgroup in which the model flags nobody returns a 1×1 matrix and .ravel() raises a shape error — or worse, in a 2-element case, silently assigns the counts to the wrong variables. §13 evaluates small subgroups at a threshold of , so degenerate confusion matrices are a realistic occurrence, not a hypothetical.

And the decision is always (proba >= threshold), never model.predict(X). predict() hardcodes 0.5. Claiming a cost-optimised threshold of in the text while computing the confusion matrix with predict() is a specific, common, and completely invisible failure: the numbers look fine, they are just answering a different question than the prose says. The only defence is to never call predict() anywhere in the project, which is the convention here.

DeLong, and why it is implemented rather than imported

§14.4 uses the DeLong test for exactly one comparison. There is no DeLong in scikit-learn or scipy, so it is implemented here, using the Sun & Xu (2014) O(n log n) reformulation rather than the original O(n²) algorithm.

The - 2 * cov[0, 1] term is the entire reason DeLong exists. Two models scored on the same clients produce correlated ROC curves: a client who is obviously going to default is ranked highly by both. Treating the two AUCs as independent would use var_a + var_b and overstate the variance of their difference, making a real difference look insignificant. Subtracting twice the covariance recovers the much smaller true variance, which is why §14.4 can resolve a difference of at p on a single test set of rows.

kind="mergesort" is there for determinism: a stable sort means re-running on the same input produces byte-identical ordering, so the reported p-value does not wobble in its last digits between runs. Small thing; free; makes "re-running reproduces every number" literally true.

The companion function that documents its own weakness
def paired_fold_test(deltas):
    """Paired t-test on per-fold differences.

    Nadeau & Bengio (2003): repeated-CV t-tests are anti-conservative because the
    training folds overlap, so the p-value is a directional indicator, not a
    calibrated error rate.
    """

Arm-vs-arm comparisons cannot use DeLong, because the 25 repeated-CV folds are not an independent sample — every pair of training folds shares roughly 60% of its rows, so the per-fold differences are positively correlated, the computed SD is too small, and the p-value is too good. The honest move is to compute it anyway (it is the best available directional signal) and to state the caveat in the docstring so it propagates into the report. §14.5's paired test on the PAY_0 ablation is reported with exactly that qualification.

15.8 tuning.py — the search, and one piece of dependency injection

Eighty-eight lines. The module docstring is the justification §7 unpacks, written where the code is rather than only in the report:

src/tuning.pymodule docstring
"""Optuna TPE search.

ROC-AUC is the objective: it is the declared primary metric (Lessmann et al., 2015),
prevalence-independent so it stays comparable across the complexity ladder, and
lower-variance across folds than PR-AUC. `aucpr` is logged every trial but not optimised.

`scale_pos_weight` is deliberately absent from the space. ROC-AUC is invariant to
monotone score transformations, so the tuner would be blind to it and pick arbitrarily;
fixing it per arm turns the imbalance study into a controlled comparison instead.
"""
src/tuning.pyexcerpt
def make_objective(X, y, folds, spw=1.0, seed=SEED, space=None, model_fn=None):
    """`model_fn(params, spw, seed) -> estimator` lets each imbalance arm be tuned
    independently while sharing one search space and one objective."""
    if model_fn is None:
        def model_fn(params, spw, seed):
            return xgb_classifier(params, spw=spw, seed=seed)

    def objective(trial):
        params = suggest(trial, space)
        for k, (tr, va) in enumerate(folds):
            est = fit_one(model_fn(params, spw, seed), X.iloc[tr], y[tr], seed=seed)
            proba = est.predict_proba(X.iloc[va])[:, 1]
            aucs.append(roc_auc_score(y[va], proba))
            aps.append(average_precision_score(y[va], proba))
            # Report after each fold so MedianPruner can abandon hopeless trials early.
            trial.report(float(np.mean(aucs)), step=k)
            if trial.should_prune():
                raise optuna.TrialPruned()
        trial.set_user_attr("pr_auc_mean", float(np.mean(aps)))
        return float(np.mean(aucs))
Design choiceWhat it buys
model_fn injected, defaulting to plain XGBoost Arm D of the imbalance study is tuned by passing lambda p, s, sd: SmoteXGB(params=p, seed=sd). One objective, one search space, one pruner, four arms. Without injection each arm would need its own near-duplicate objective, and near-duplicate objectives drift.
trial.report(..., step=k) inside the fold loop Pruning granularity becomes a fold, not a trial. A hopeless parameter set is abandoned after fold 2 instead of burning all five. of the trials were pruned, which is where most of the time saving comes from.
The reported value is the running mean np.mean(aucs) MedianPruner compares like with like: at step k it compares this trial's mean over k+1 folds against other trials' means over the same number of folds. Reporting the single latest fold's AUC instead would make the comparison noisier and prune good trials that happened to draw a hard fold first.
set_user_attr("pr_auc_mean", ...) PR-AUC is logged every trial and never optimised, exactly as the docstring promises. It can therefore be reported, and the claim "we tracked it but did not chase it" is checkable against the study database.

Why the study is persisted, and why n_jobs=1

SQLite storage with load_if_exists=True makes the search resumable and, more importantly, makes it inspectable after the fact. The -trial history is what lets §7 show that the objective surface is nearly flat — of ROC-AUC separates the best trial from the worst completed one, against a pooled fold-SD of — rather than merely asserting it. The remaining arithmetic counts both COMPLETE and PRUNED trials towards the budget, so a resumed study converges on total rather than running more.

Thread oversubscription is the quiet performance trap of this stack. XGB_FIXED sets n_jobs=-1, so each fit already saturates every core. Setting Optuna's n_jobs above 1 would launch several such fits concurrently, and on an n-core machine you would get n processes each spawning n threads — n² threads fighting over n cores, with context-switching overhead that typically makes the whole search slower than serial. One parallelism layer at a time.

15.9 The anatomy of one experiment

With the package doing the work, each experiment script is thin: it assembles components, and almost its only original content is the set of arms it defines and the notes it writes. exp03_imbalance is the most instructive because it touches nearly every module.

Interactive · walking python -m experiments.exp03_imbalance down the layers

Six stages, in execution order. Each shows the real lines and the invariant that stage is responsible for. The point of the exercise is that no stage trusts the next one — each enforces its own contract and fails loudly rather than degrading quietly.

What the thinness is worth

Count what exp03 actually decides for itself: the four arm definitions, the trimmed SMOTE trial budget (SMOTE_TRIALS = 60, with the comment "each trial resamples to ~2x rows, so the budget is trimmed"), and the notes text. Everything else — the folds, the fitting, the early-stopping slice, the metric definitions, the SD convention, the threshold search, the JSON schema — comes from the package and is therefore identical to what exp01 and exp14 used. That is what makes the ladder table in §6 and the imbalance table in §8 directly comparable: not care, but shared code.

Why does exp03 tune arms C and D with their own Optuna studies instead of reusing arm A's parameters at a different scale_pos_weight?

Because reusing A's parameters would confound the thing being measured. The question is "does reweighting help?", and the fair version of that question is "does the best achievable reweighted model beat the best achievable unweighted model?" If you took parameters tuned for spw=1 and simply switched spw to , any underperformance could be dismissed as "you did not re-tune for it" — and legitimately so, since reweighting changes the gradient and Hessian magnitudes and therefore interacts with min_child_weight, reg_lambda and eta.

Giving each arm its own study removes that objection, at a cost of roughly tripling the experiment's runtime. The finding that reweighting buys nothing in ranking (§8) is then a statement about the strategy rather than about one unlucky parameter transplant — which is precisely why scale_pos_weight is excluded from the search space and fixed per arm instead (§7.3). The two decisions are the same decision seen from two directions.

Suppose you deleted require_artifact and made every experiment re-tune when best_params.json was missing. Name a concrete way the report could then become internally inconsistent.

Here is one path. You run exp02 and get a tuned configuration. You then run exp06 (feature groups), which finds best_params.json present and uses it. Later you delete artifacts/ to reclaim disk space, or move to another machine, and run exp11 (SHAP) — which, under the hypothetical, silently re-tunes. TPE is seeded, but it is tuning inside a different script that may pass a different feature set, a different spw, or simply a different number of trials. You now have two different "tuned XGBoost" models in the project.

The report then says "the tuned model achieves ROC-AUC X (§6) and its most important feature is Y with mean|SHAP| Z (§11)", and those two sentences describe different models. Nothing errors, no number looks implausible, and the inconsistency is undetectable from the outputs alone — the SHAP values are perfectly valid, just for a model that appears nowhere else. Exiting with "MISSING ARTIFACT … Produced by WP6. Run that first." turns an invisible inconsistency into a thirty-second inconvenience.
