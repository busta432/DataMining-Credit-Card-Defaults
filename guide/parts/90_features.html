Section 10Feature studies: where the signal actually lives

Five ablations, 28 arms, one purpose: establish empirically what the model is learning from, so that every claim about the data is measured rather than asserted. Two of these experiments exist because Phase 1 made a specific commitment, and one of those predictions turns out to be neither confirmed nor refuted — which is itself the honest finding.

10.1 Encoding: four representations, one conclusion

PAY_n is an ordinal code with a non-monotonic relationship to default. There are three defensible ways to hand that to a tree, plus one arm included purely to prove a point about scaling.

ArmfeaturesROC-AUC ± SDPR-AUCWhat it tests

All four sit within ROC-AUC of each other, against a fold-SD of . None is distinguishable. So the choice is made on reasoning, not on the numbers — which is the more interesting position to be in.

Native integers are carried forward, for three reasons
  1. Non-monotonicity is recoverable by stacking splits. A tree can learn "PAY_0 < 0.5" and then, inside that branch, "PAY_0 < −1.5", isolating code −2 from codes −1 and 0. Integer encoding costs depth, not expressible functions. This is the key insight — the usual objection to integer-encoding a categorical ("it imposes a false ordering") applies to linear models, where the coefficient really does impose one. Axis-aligned splitting does not.
  2. It preserves the recency gradient. Six distinct integer columns keep Phase 1's measured gradient intact (Spearman ρ rising 0.143 at April → 0.292 at September). One-hot expands to columns, scattering each month's signal across eleven sparse dummies, and §7's colsample_bytree = then samples columns in a way that no longer corresponds to sampling months.
  3. It avoids a live library incompatibility. See the trap below.
The enable_categorical trap — version-specific and real

The native_categorical arm is the numerically best of the four ( vs ) — by an amount well inside one SD, but best. It is still not carried forward, and the reason is a hard constraint rather than a preference.

XGBoost 3.4 with enable_categorical=True emits categorical split nodes, which partition a set of levels rather than testing a threshold. shap 0.52's interventional TreeSHAP cannot traverse them:

Research question 2 is entirely about post-hoc explainability. Choosing an encoding that gains 0.0009 ROC-AUC — one eighth of a fold-SD — at the cost of making §11 and §12 impossible would be trading the answer to half the research questions for noise. Naming the exact exception is also better evidence than "we had compatibility issues".

The signed-log arm proves scale invariance exactly

Applying sign(x)·log1p(|x|) to LIMIT_BAL, all six BILL_AMT and all six PAY_AMT columns changes ROC-AUC by +0.00000 — identical to the digit, not merely close. §3 argued this must be true: a strictly increasing transform preserves the sorted order of every column, so the same candidate splits exist and the same tree is learned. The arm turns the argument from theory into measurement, and it is the cleanest possible reply to the Phase 1 recommendation to scale features — that recommendation was for distance and gradient learners, and this one line of evidence shows it does not apply here.

Phase 1 predicted a loss from aggregation. The engineered-only arm is directionally consistent with that — it is the worst arm, and its PR-AUC drop ( vs ) is larger than its ROC-AUC drop, which is what losing resolution in the high-threshold region looks like. But the effect does not clear the noise floor, and the correct report sentence says so: "directionally consistent with the Phase 1 prediction but not statistically distinguishable at one fold-SD."

Resisting the temptation to call an improvement is worth marks. It is half a fold-SD.

Why the RFE arm exists — removing the width confound

raw_plus_engineered has 40 columns against the baseline's 23, and more columns can help purely by giving colsample_bytree a larger pool to draw from. The RFE arm eliminates that confound by recursively eliminating back down to 23 features from the combined pool — an equal-width comparison. It retains engineered features and scores , which is between the two, and tells you something the other arms cannot: RFE voluntarily kept UTIL_1–3, N_DELINQ, MAX_DELINQ, DELINQ_TREND and BILL_TREND while discarding PAY_5, BILL_AMT3/4/6 and five of the six PAY_RATIO_n. So the engineered features are not useless — several are preferred over raw columns — they are just substitutes for information the raw columns already carry.

The NaN decision, and why it is a library-feature argument

PAY_RATIO_n = PAY_AMTn / BILL_AMTn is undefined where the statement balance is zero, and meaningless where it is negative — and Phase 1 §1.6 documented 1,930 rows with a negative BILL_AMT (credit balances from overpayment or refunds). Three options existed:

  • Impute a sentinel such as 0 or −999: tells the model a falsehood, and a sentinel in a numeric column creates a split point with no semantic meaning.
  • Drop the rows: discards 6.4% of the data, non-randomly — overpayers are not a random subsample.
  • Emit np.nan and let XGBoost's sparsity-aware split finding learn a default direction per node (§3.6). ✅

The third is chosen, and it is worth noting in Solution precisely because it is a feature of the chosen library being used deliberately rather than a generic preprocessing step. The direction is learned from the gradient statistics, so the model discovers for itself whether "no meaningful bill" behaves more like a payer or a non-payer. verify.py asserts no column contains inf, which is the real hazard — division by zero producing inf rather than NaN would poison the gradient sums rather than route around them.

This matters twice: it means dropping them is nearly free, and it sets up §13's actual question, which is whether the financial columns proxy for them anyway.
Why leave-one-out and only-one must both be reported

Each view answers a different question and each is misleading alone. Only-one asks "is this group informative?" and over-credits redundant groups — bill looks valuable. Leave-one-out asks "is this group necessary?" and under-credits them — bill looks worthless. Neither is wrong; they are answering "informative" and "necessary", which differ exactly to the extent that features are correlated. A report that showed only one view would be making a claim the other view contradicts, and the obvious question in a viva is the one you did not run.

10.5 The learning curve: is the model data-limited or feature-limited?

Five training fractions, five seeds each, with both the training and validation curves recorded. This distinguishes two situations that look identical if you only plot validation performance, and the distinction carries the central claim of the Summary.

Validation ROC-AUC (solid) and training ROC-AUC (dashed), with the shaded band showing ± one SD across seeds. Two things to read: the validation curve flattening, and the gap between the curves staying roughly constant rather than closing.

Why a plateau is a stronger claim than an assertion

Validation ROC-AUC rises at 10% of the data to at 100%. Half the data already reaches , and the final step from 75% to 100% adds against a fold-SD of . The curve has flattened.

Now the diagnostic that the training curve enables. There are two distinct reasons a validation curve plateaus:

  • High variance — the model is overfitting, the train–validation gap is large and shrinking with more data, and more data would close it. The fix is more data.
  • High bias / feature ceiling — the gap is small and stable, and both curves have converged. More data cannot help, because the features do not contain the missing information. The fix is better features.

The measured gap is at 10% of the data and at 100% — essentially unchanged. So this is the second case: a feature-set ceiling. Having the training curve is what licenses that conclusion; the validation curve alone is consistent with both stories.

The three-legged argument this feeds into

The Summary's central claim is that performance here is bounded by what a six-month billing snapshot can observe — it cannot see job loss, illness, divorce or income shock. Three independent pieces of evidence support it, and none would be sufficient alone: (1) the learning curve is flat with a stable gap (this section); (2) the whole searched hyperparameter space is worth under one fold-SD (§7); (3) a single column, PAY_0, is worth — more than tuning and more than five extra months of history combined (§14). An argument assembled from three different experiments is much harder to dismiss than an assertion that the dataset is "hard".

Self-check: the native_categorical arm scored highest. Isn't rejecting it cherry-picking?

It would be if the rejection were on performance grounds, or if the arm were hidden. Neither applies: the arm is reported in the table with its winning number, and the stated reason is a hard tooling constraint — shap 0.52 raises NotImplementedError: Categorical split is not yet supported on categorical split nodes.

The quantities being traded are also wildly asymmetric. The gain is ROC-AUC, about one eighth of a fold-SD, i.e. not distinguishable from zero. The cost is the entire answer to research question 2. Declaring the trade-off and the exception is the transparent move; silently dropping the arm would be the cherry-pick.

Self-check: if k = 3 months is within one SD of k = 6, why does the final model use all six?

Because "within one fold-SD" means not distinguishably worse, not better. The point estimate for k = 6 is still higher than k = 3 ( vs ), the data is already collected, and there is no cost to using it. Discarding available columns to chase parsimony the evidence does not demand would be the wrong move.

The recency finding is a statement about future data collection, not about this model: if a lender were specifying a new application-scoring pipeline, three months of statement history would capture nearly all the obtainable signal, and that is a real operational saving. That is why it lands in Summary — as a practical implication — rather than changing the final feature set.
